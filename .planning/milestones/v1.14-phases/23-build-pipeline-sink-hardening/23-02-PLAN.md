<objective>
Teach the build worker (`services/worker` submodule) to run argv jobs without a shell (SEC-EXEC-02, D-02, D-03, D-04). The worker must keep accepting the legacy `cmd` field so the API and the worker can be deployed in either order.

1. **Tracer (Task 1).** A socket.io `job` carrying `argv` goes through `runJob` → `validateJob` → `validateArgv` → `runArgv` → `exec.spawn(BUILDER_PROGRAM, argv, { shell: false })`. The spec comes first.
2. **Legacy visibility + cleanup (Task 2).** A `cmd`-only job logs a warning (D-03), the dead `lgtm` markers go (D-15), and the worker work is committed in the worker repo.

Purpose: the remote-builder half of SEC-EXEC-02 lives in the worker. This plan has no file overlap with 23-01, so it runs in wave 1 in parallel. The API half (the job gains `argv`) is plan 23-04, which also bumps the parent's submodule pointer.
Output: worker commit(s) on the local `services/worker` `main` branch. **Not pushed here.** Plan 23-05 pushes the worker first, then the parent (CI runs `git submodule update --init --recursive`, so an unpushed worker commit would break the parent pipeline).
</objective>

## Flagged Assumptions (edge probe: unclassified, surfaced not dropped)

- **A-23-02-1 (SEC-EXEC-02, unclassified).** The argv flag allowlist (`owner udid fcid mac git branch id workdir env` plus `--dry-run`) is assumed to be the complete set the API emits. Adding a builder flag in the API later needs a worker release first, or jobs carrying the new flag are refused with `Invalid argv`. The refusal is visible in job-status, not silent.
- **A-23-02-2.** An API env value containing a shell metacharacter or a backslash is refused as it is today, because `isArgumentSafe` now runs per element, where before it ran over the whole string. Relaxing that for `--env=` would be a separate decision, because the bash builder is not audited for safe interpolation.
