Facts (from research; re-verify):
- **Old job.** `/etc/cron.daily/couchdb-log-retention` (an exec wrapper) runs `/usr/local/sbin/couchdb-log-retention.sh` through `/etc/crontab` `25 6 * * *`. It locks `/var/lock/couchdb-log-retention.lock` and logs to `/var/log/couchdb-log-retention.log`. Every run since 2026-09-24 has logged `nothing to delete (resp head: )`, because the DHI CouchDB image has no curl.
- **Expected first dry run** (2026-10-01 numbers, which drift daily):
  - build records: about 103 expired;
  - deploy root: 4 record folders (about 44K) and 0 orphans;
  - repos root: 103 record folders (about 29M) and 61 orphans (about 227M, mtimes 2021-07 to 2022-05);
  - audit: about 30 docs past 365 days, plus whatever aged out since.
- **Assumption A7.** It is unproven that a standalone container on `thinx_internal` resolves the stack alias `couchdb`. If the dry run fails on host resolution, rerun with `COUCHDB_HOST=thinx_couchdb` (the swarm service name) in front of the wrapper. Whatever works goes into the cron line.
- **Wrapper contract (plan 26-04).**
  - Arguments: none or `--dry-run`, or `--apply --roots <deploy|repos|deploy,repos|none> [--no-audit]`.
  - Roots are mounted read-only unless `--apply`.
  - The wrapper exits 1 unless the run printed its OK line.
  - It logs to `/var/log/thinx-log-retention.log` and takes the lock `/var/lock/thinx-log-retention.lock`.
- **Filesystem checks.** Depth-limited only (`-mindepth/-maxdepth`), because a full-depth find on gluster takes over 5 minutes. Print counts only.
