Facts verified at planning time (2026-09-29). Re-verify them; do not trust them blindly.
- `readSecret(name, default)` in `lib/thinx/secrets.js` returns the trimmed `/run/secrets/NAME` file, else `process.env[name]`, else the default (`null`). It caches per name and has a path-containment check. `_resetCacheForTests()` clears the cache. It uses the plain `fs` module, so a spec can wrap `fs.existsSync`/`fs.readFileSync`.
- Existing readers already on `readSecret`: `globals.js:98` (REDIS_PASSWORD), `database.js:16-17` (COUCHDB_*), `git.js:245` (GIT_KEY_PASSPHRASE).
- Direct env reads to convert in this plan: `owner.js:13` and `transfer.js:12` (MAILGUN_API_KEY, at module load); `messenger.js:128-129` and `:147-148` (SLACK_BOT_TOKEN); `router.slack.js:29` (SLACK_CLIENT_SECRET, per request); `notifier.js:43` and `:257` (SLACK_WEBHOOK); `redis-health.js:44` (SLACK_WEBHOOK unless `opts.webhook` is given).
- `messenger.js` hard-codes `this.DISABLE_SLACK = true` in the constructor, so production never reaches `initSlack`'s token check. Leave that flag alone. The spec calls `Messenger.prototype.initSlack` on a fake `this` with `DISABLE_SLACK: false`.
- `router.slack.js` `/api/slack/redirect` always ends with `xres.redirect("https://" + WEB_HOSTNAME + "/app/#/profile/help")`; the token exchange with slack.com runs in the background. `ZZ-RouterOAuthSpec` only checks the redirect.
- Every target module loads locally with `ENVIRONMENT=development COUCHDB_USER=u COUCHDB_PASS=p` (config from `spec/mnt/data/conf`). The locally green spec set today (with GitSpec, SanitkaSpec, BuilderRemoteJobSpec, BuilderPathSpec added) is 235 specs, 0 failures. `MessengerSpec` and `03-RsakeySpec` need Redis and `/mnt/data` and fail locally; they are CI-only.
- The developer's shell exports `MAILGUN_API_KEY`. The spec must save and restore it, and no command may print it.
- In CI the whole jasmine suite runs in one process, with `spec/helpers/bootstrap.js` starting THiNX once, and CI has real values for these env vars. That is why every swap in the spec must be undone.
- Node's module loader and `fs-extra` read real files through `fs`. A blanket `fs.readFileSync` stub (as in SecretsSpec) would break any `require` made while it is active, so the wrappers here must delegate every path they do not own.
</context>

Add three top-level helpers that the later cases and plan 24-03 reuse:
- `withSecrets(spec, fn)`. `spec` maps a credential name to `{ file }`, `{ env }`, `{ file, env }` or the string `"absent"`. It saves the current `process.env` value of every named key, then sets or deletes it. It wraps `fs.existsSync` and `fs.readFileSync` so that only `/run/secrets/<NAME>` for the named keys is answered: existsSync is true and readFileSync returns the value for `file` entries, existsSync is false for the others. Every other path is delegated to the saved originals, because the module loader and fs-extra read real files during fresh requires. It calls `_resetCacheForTests()`, runs `fn` (awaiting a returned promise), and in `finally` restores the fs functions and env (deleting a key that was originally undefined), then resets the cache again.
- `freshRequire(relPath, stubs)`. It resolves the target id with `require.resolve`. For each stub (a module id mapped to fake exports) it makes sure the real module is loaded, saves its `require.cache` entry's `exports`, and replaces them with the fake. It saves and deletes the target's cache entry, requires the target fresh, and returns `{ mod, restore }`. `restore()` puts the saved target entry back (or deletes it when there was none) and restores every stubbed `exports`. Always call `restore()` in `finally`.
- `captureLogs(fn)`. It swaps `console.log` for a collector, restores it in `finally`, and returns the collected lines as strings.
- Fake values are obvious throwaways, such as `spec-fake-mailgun-file-7c1e` and `spec-fake-mailgun-env-2b9d`. Never use a URL or token shape that a secret scanner would flag.
