<objective>
Close UAT gap G-36-3 (UAT test 3, requirement BUILD-01). Binding operator direction, 2026-10-12, verbatim: "Remove inline logs from device build history".

Today the Vue device detail page does two things the operator does not want:
- every Build History row is itself a full-log trigger (a focusable button-role row with click, Enter and Space handlers), so browsing or tabbing the history starts the heavy GET /api/v2/logs/build/:id download;
- a separate last-build log card under Build History renders log lines inline in a terminal-styled block.

This plan makes the device history summary-only and moves the full log behind an explicit per-row "Open build log" button. That mirrors History.vue since console commit 7d39da4 (35 WR-01), minus History's mouse row-click shortcut, which the operator's direction rules out on this page.

1. **Tracer (Task 1).** Write a failing render test of the whole real DeviceDetail page after the real loadDevice(). Then make the page summary-only (remove the card, make the rows inert, add the button) and commit both, signed, in the console.
2. **Expansion (Task 2).** Update the Cypress device-detail spec, which still expects the removed card and would fail in console CI. Prove the unit checks bite with two mutations. Run the full unit chain and ESLint, then make the signed parent gitlink bump. Nothing is pushed.

Purpose: the device page lists builds quickly and loads a full build log only when the operator explicitly asks for it.
Output: three console files changed in signed thinx-staging commits, and one signed parent gitlink commit. All of it stays local for the orchestrator to push.
</objective>

## Deferred (out of scope for 36-02, per the orchestrator brief; record in the SUMMARY, do not implement)

- **Backend full-log payload size.** GET /api/v2/logs/build/:id is heavy:
  - `lib/thinx/buildlog.js` `_fetch` reads the whole `build.log` with `fs.readFileSync` from GlusterFS (`/mnt/gluster/thinx/deploy`) on the API event loop;
  - `lib/thinx/util.js` `respond` JSON-serializes the Node Buffer as a `{type:'Buffer',data:[…]}` byte array, measured at about 3.4x the log size (2 MB log → 6.8 MB JSON);
  - neither Traefik nor Express compresses it.
  
  After this plan the request is made only on an explicit "Open build log". The opened dialog stays as slow as the payload. Possible directions, not planned here: return the log as a string, add compression, cap the size or load the tail first. Source: `.planning/debug/device-build-history-full-logs.md` (missing item 3).
