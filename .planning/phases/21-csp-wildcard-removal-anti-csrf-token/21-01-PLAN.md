<objective>
Implement the API-side half of the double-submit anti-CSRF token (SEC-CSRF-01, per the locked design in `21-CONTEXT.md`): a non-httpOnly `XSRF-TOKEN` cookie the server issues, a dedicated priming endpoint so a cold (cookieless) console can obtain the cookie before its first POST, and a `verifyCsrfToken` check applied to the cookie-session login/account POST routes. The check is env/config-driven fail-open (log + allow) by default, flippable to hard-enforce (403) without a code change.

Purpose: close the HawkScan "Anti-CSRF Tokens" (plugin 20012) finding server-side, without touching the JWT/X-Access-Token device/build API surface (not CSRF-prone, out of scope per REQUIREMENTS.md).

## Protected route set (REVISED per plan-checker BLOCKER 2 — reconciled against the real route definitions)

`21-CONTEXT.md`'s D-02 listed the protected set informally as `/login, /api/login, /api/v2/login, /user/create, /user/password/reset` with the stated INTENT "cookie-session login/account POSTs only." That enumeration was factually incomplete: it omitted the Vue console's password-reset/-set flow (`PasswordReset.vue` -> `store/auth.js` -> `$api.$post('/password/reset')` / `$api.$post('/password/set')`, which resolve through `api.js`'s `apiPath='/api/v2'` to `/api/v2/password/reset` and `/api/v2/password/set`) and the classic console's reset-confirm POST (`password.js` -> `/api/user/password/set`). Honoring the INTENT of D-02 (protect every cookie-session/reset-key auth POST both consoles hit) rather than its incomplete literal list, the canonical protected set — verified against `lib/router.auth.js` and `lib/router.user.js` — is these 7 routes:

| # | Route | Which console hits it | Route def |
|---|-------|-----------------------|-----------|
| 1 | `POST /api/login` | classic login.js + classic auth.js | router.auth.js:336 |
| 2 | `POST /api/v2/login` | Vue Login.vue | router.auth.js:350 |
| 3 | `POST /api/user/create` | classic register-form | router.user.js:191 |
| 4 | `POST /api/user/password/reset` | classic forget-form | router.user.js:211 |
| 5 | `POST /api/user/password/set` | classic password.js reset-confirm | router.user.js:201 |
| 6 | `POST /api/v2/password/reset` | Vue PasswordReset.vue initiate | router.user.js:153 |
| 7 | `POST /api/v2/password/set` | Vue PasswordReset.vue confirm | router.user.js:163 |

Deliberate exclusion, documented: `POST /api/gdpr` (classic `auth.js` gdpr-form) is a POST-authentication consent action (a session cookie already exists by then, so double-submit would work), is NOT part of the scanner's login-page finding, and is NOT in D-02's list. It keeps its hidden `_csrf` field (Plan 21-02 Task 1) for the scanner's static check; server-side validation of `/api/gdpr` is a low-risk follow-on, not wired here to avoid scope creep beyond the checker's directive. `POST /api/v2/user` (router.user.js:144) is not hit by either console and is left unprotected.

Output: `lib/middleware/csrf.js`, the 7 routes wired, the `GET /api/csrf-token` + `GET /api/v2/csrf-token` priming endpoints, a new `debug.csrf_enforce` config flag (mirrors `debug.allow_http_login`), and a passing regression spec.

No new npm dependency is introduced — `cookie-parser` is already a `package.json` dependency (currently unmounted) and token generation uses Node's built-in `crypto`. The package-legitimacy gate does not apply to this plan.

  <name>Task 1: CSRF middleware module (double-submit cookie + verify) and enforce-flag config</name>
  <files>lib/middleware/csrf.js, conf/config-sample.json, conf/config-localhost.json, spec/mnt/data/conf/config.json, spec/jasmine/ZZ-CSRFSpec.js</files>
  <behavior>
    - `ensureXsrfCookie(req, res, next)`: if `req.cookies['XSRF-TOKEN']` is absent/empty, generate `crypto.randomBytes(24).toString('hex')`, `res.cookie('XSRF-TOKEN', token, { httpOnly: false, secure: false, sameSite: 'lax', domain: short_domain, path: '/' })`, and stash it on `res.locals.xsrfToken` so the priming endpoint can echo it. Always calls `next()`.
    - `issueCsrfToken(req, res)`: a GET handler that calls `ensureXsrfCookie(req, res, () => {})` to guarantee a cookie is set, then responds `Util.respond(res, { csrf_token: req.cookies['XSRF-TOKEN'] || res.locals.xsrfToken })`. This is the priming endpoint's handler — it is NOT wrapped in verifyCsrfToken (GET, and it is the bootstrap that mints the token).
    - `verifyCsrfToken(req, res, next)`: reads `req.cookies['XSRF-TOKEN']` and `req.headers['x-xsrf-token']` (Express lower-cases header names). If both are non-empty strings of equal length and `crypto.timingSafeEqual(Buffer.from(cookieVal), Buffer.from(headerVal))` is true -> `next()`.
    - Failure (missing either side, length mismatch, or mismatch) AND `isEnforced()` false -> log `console.log("⚠️ [warning] CSRF token missing/mismatched for " + req.method + " " + req.originalUrl + " (fail-open, not enforced)")` and call `next()` anyway.
    - Failure AND `isEnforced()` true -> `Util.failureResponse(res, 403, "csrf_token_invalid")`, do NOT call `next()`.
    - `isEnforced()`: `process.env.CSRF_ENFORCE === 'true'` short-circuits true; otherwise `app_config.debug.csrf_enforce === true` (defaults to false/fail-open if the key is absent — production's mounted config will not have it until Plan 21-05).
  </behavior>
  <action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (untrusted, possibly attacker-controlled cross-site page) -> API cookie-session POST routes | The 7 routes rely on ambient cookie/reset-key auth; a cross-site form/fetch can trigger the request even without reading the response (classic CSRF) |
| Static-nginx-served console page -> API | The login/reset PAGES are served by nginx `location /` (NOT proxied to Express), so the reactive `ensureXsrfCookie` never fires on a pure page load — the priming GET is the only thing that mints a cookie for a cold session |
| Browser JS (console app code, trusted origin) -> XSRF-TOKEN cookie | The cookie is deliberately non-httpOnly so legitimate console JS can read and echo it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-01 | Spoofing/Tampering | The 7 protected cookie-session/reset-key POST routes | mitigate | Double-submit `XSRF-TOKEN` cookie + `X-XSRF-TOKEN` header compared via `crypto.timingSafeEqual`; hard-enforced once `debug.csrf_enforce`/`CSRF_ENFORCE` flips true (Plan 21-05) |
| T-21-02 | Information Disclosure | XSRF-TOKEN cookie (non-httpOnly by design) | accept | Double-submit inherently requires JS-readability; an attacker who can read this cookie already has full-DOM XSS (equivalent to session hijack). Broader inline/eval XSS surface tracked as deferred SEC-CSP-02 |
| T-21-03 | Tampering | Token generation/comparison | mitigate | `crypto.randomBytes(24)` (192 bits); `crypto.timingSafeEqual` constant-time comparison |
| T-21-04 | Denial of Service | `debug.csrf_enforce` misconfig OR cold-session lockout | mitigate | Fail-open default; staged rollout (21-04 fail-open verify -> 21-05 enforce after cold-session verify); `GET /api/(v2/)csrf-token` priming endpoint (BLOCKER 1 fix) guarantees a cold, statically-served console page can obtain a cookie before its first protected POST; `CSRF_ENFORCE` env override enables config-free rollback |

No package-manager installs are part of this plan (`cookie-parser` already in `package.json`; `crypto` is Node core) — the Package Legitimacy Gate does not apply.
