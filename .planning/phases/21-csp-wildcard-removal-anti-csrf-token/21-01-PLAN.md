<objective>
Implement the API-side half of the double-submit anti-CSRF token (SEC-CSRF-01, per the locked design in `21-CONTEXT.md`): a non-httpOnly `XSRF-TOKEN` cookie the server issues on any response, and a `verifyCsrfToken` check applied ONLY to the four cookie-session login/account POST routes (`/api/login`, `/api/v2/login`, `/api/user/create`, `/api/user/password/reset`). The check is env/config-driven fail-open (log + allow) by default, flippable to hard-enforce (403) without a code change.

Purpose: close the HawkScan "Anti-CSRF Tokens" (plugin 20012) finding server-side, without touching the JWT/X-Access-Token device/build API surface (not CSRF-prone, out of scope per REQUIREMENTS.md).
Output: `lib/middleware/csrf.js`, the four routes wired, a new `debug.csrf_enforce` config flag (mirrors `debug.allow_http_login`), and a passing regression spec.

No new npm dependency is introduced — `cookie-parser` is already a `package.json` dependency (currently unmounted) and token generation uses Node's built-in `crypto`. The package-legitimacy gate does not apply to this plan.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: CSRF middleware module (double-submit cookie + verify) and enforce-flag config</name>
  <files>lib/middleware/csrf.js, conf/config-sample.json, conf/config-localhost.json, spec/mnt/data/conf/config.json, spec/jasmine/ZZ-CSRFSpec.js</files>
  <behavior>
    - `ensureXsrfCookie(req, res, next)`: if `req.cookies['XSRF-TOKEN']` is absent/empty, generate `crypto.randomBytes(24).toString('hex')` and `res.cookie('XSRF-TOKEN', token, { httpOnly: false, secure: false, sameSite: 'lax', domain: short_domain, path: '/' })` (same `short_domain` derivation as the session cookie, see interfaces). Always calls `next()`.
    - `verifyCsrfToken(req, res, next)`: reads `req.cookies['XSRF-TOKEN']` and `req.headers['x-xsrf-token']` (Express lower-cases header names). If both are non-empty strings of equal length and `crypto.timingSafeEqual(Buffer.from(cookieVal), Buffer.from(headerVal))` is true -> `next()`.
    - If the check fails (missing either side, length mismatch, or mismatch) AND `isEnforced()` is false -> log `console.log("⚠️ [warning] CSRF token missing/mismatched for " + req.method + " " + req.originalUrl + " (fail-open, not enforced)")` and call `next()` anyway.
    - If the check fails AND `isEnforced()` is true -> `Util.failureResponse(res, 403, "csrf_token_invalid")` and do NOT call `next()`.
    - `isEnforced()`: `process.env.CSRF_ENFORCE === 'true'` short-circuits to `true`; otherwise reads `app_config.debug.csrf_enforce === true` (defaults to `false`/fail-open if the key is absent — production's host-mounted `/mnt/data/conf/config.json` will not have this key until Plan 21-05 adds it, so the default MUST be safe).
  </behavior>
  <action>
    Create `lib/middleware/csrf.js` as a factory module mirroring `lib/middleware/requireAdmin.js`'s shape: `module.exports = function (app) { ... return { ensureXsrfCookie, verifyCsrfToken }; };`. Internally `require("../thinx/globals")` for `app_config` and `require("../thinx/util")` for `Util.failureResponse`. Add a `"csrf_enforce": false` key to the `debug` block in `conf/config-sample.json`, `conf/config-localhost.json`, and `spec/mnt/data/conf/config.json` (per D-03 in `21-CONTEXT.md`: reuse the `app_config.debug.allow_http_login` flag pattern for the enforce flag; env override `CSRF_ENFORCE` takes precedence for a config-free rollback).   </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (untrusted, possibly attacker-controlled cross-site page) -> API cookie-session POST routes | The 4 routes rely on the ambient `x-thx-core` session cookie; a cross-site form/fetch can trigger the request even without reading the response (classic CSRF) |
| Browser JS (console app code, trusted origin) -> XSRF-TOKEN cookie | The cookie is deliberately non-httpOnly so legitimate console JS can read and echo it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-01 | Spoofing/Tampering | `/api/login`, `/api/v2/login`, `/api/user/create`, `/api/user/password/reset` | mitigate | Double-submit `XSRF-TOKEN` cookie + `X-XSRF-TOKEN` header compared via `crypto.timingSafeEqual` in `lib/middleware/csrf.js:verifyCsrfToken`; hard-enforced once `debug.csrf_enforce`/`CSRF_ENFORCE` flips true (Plan 21-05) |
| T-21-02 | Information Disclosure | XSRF-TOKEN cookie (non-httpOnly by design) | accept | Double-submit inherently requires JS-readability; an attacker who can read this cookie already has full-DOM XSS capability equivalent to session hijack — no new capability added. Broader inline/eval XSS surface tracked separately as deferred SEC-CSP-02 |
| T-21-03 | Tampering | Token generation/comparison | mitigate | `crypto.randomBytes(24)` (192 bits) token; `crypto.timingSafeEqual` constant-time comparison avoids a timing side-channel |
| T-21-04 | Denial of Service | `debug.csrf_enforce` misconfiguration locking out all logins | mitigate | Fail-open default (`false`); staged rollout across Plans 21-04 (fail-open deploy + functional verify) then 21-05 (flip to enforce only after verification); `CSRF_ENFORCE` env override allows a config-only rollback with no redeploy |

No package-manager installs are part of this plan (`cookie-parser` already in `package.json`; `crypto` is Node core) — the Package Legitimacy Gate does not apply.
</threat_model>
