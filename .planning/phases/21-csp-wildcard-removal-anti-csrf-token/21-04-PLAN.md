## CONFIRMED DEPLOY TOPOLOGY (verified live on the swarm 2026-07-05 — supersedes the ambiguity in prior revisions of this plan)

- `app.thinx.cloud` = `thinx_api` (`thinxcloud/api:latest`, node `micro`) — the bare API. `app.get("/")` returns a JSON healthcheck, NOT a login form. This is where Plan 21-01's code (CSRF middleware, priming endpoints, the 7 protected routes) actually lands.
- `rtm.thinx.cloud` = the LEGACY console (`thinx_console`, `:swarm` tag, node `core`). Its own nginx serves the static classic console (Plan 21-02/21-03's `services/console/src` build) AND proxies `/api`, `/device`, etc. through to `thinx_api`. HawkScan targets `rtm.thinx.cloud` — this is correct, since it fronts BOTH the login form the scanner inspects AND the proxied API responses.
- `console.thinx.cloud` = the VUE console (`thinx/console:vue`, node `core`). It calls the API cross-origin DIRECTLY at `app.thinx.cloud` (not proxied) — `mixins/hostnames.js`'s `API` hostname resolves from `VUE_APP_API_HOSTNAME`, which is `app.thinx.cloud`.
- `CORS_ALLOWED_ORIGINS=https://console.thinx.cloud,https://rtm.thinx.cloud` and `API_HOSTNAME=app.thinx.cloud` on the `thinx_api` service — this is what makes the Vue console's cross-origin `fetch(..., { credentials: 'include' })` calls (including the `GET /api/v2/csrf-token` prime) work against `app.thinx.cloud`.

A prior revision of this plan implied "the API deploys to `rtm.thinx.cloud`" — that was imprecise. `rtm.thinx.cloud` is a CONSOLE that proxies to the API; the API's own deploy target is `app.thinx.cloud`. This distinction matters for Task 2's verification: the priming `GET /api/(v2/)csrf-token` resolves DIFFERENTLY per console — via `rtm.thinx.cloud`'s own `/api` proxy for the legacy console, and directly to `app.thinx.cloud` for the Vue console — but in both cases the `Set-Cookie: XSRF-TOKEN=...` response carries `Domain=.thinx.cloud` (per Plan 21-01's domain-scoping algorithm, matching the existing session-cookie scoping), so the SAME cookie is valid and sent on subsequent requests to any of the three `*.thinx.cloud` hosts, regardless of which one actually minted it.

Purpose: per the locked rollout decision in `21-CONTEXT.md` ("Rollout: fail-open + log, then flip to enforce"), the API's CSRF check MUST already be live and observed working in fail-open mode BEFORE enforcement is turned on, so a wiring mismatch cannot lock out staging login.
Output: `thinx-device-api` (carrying `app.thinx.cloud`'s API deploy) and `services/console` (carrying both `rtm.thinx.cloud` and `console.thinx.cloud`'s console deploys) both on `thinx-staging` at the tip commit including this phase's changes; CI green; both consoles confirmed functional in a browser.
