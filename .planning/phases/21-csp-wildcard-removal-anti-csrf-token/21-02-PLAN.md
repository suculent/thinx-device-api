<objective>
Wire the console-side half of the double-submit anti-CSRF token (SEC-CSRF-01) into BOTH consoles in the `services/console` submodule: the legacy AngularJS/jQuery console (`services/console/src`) and the Vue console (`services/console/vue`). Add the hidden `_csrf` form field the scanner's plugin 20012 inspects to every classic POST login/account form; prime the `XSRF-TOKEN` cookie on login/reset page load via `GET /api/csrf-token` (Plan 21-01's new endpoint); and send the real `X-XSRF-TOKEN` header on every protected login/account XHR call.

Purpose: satisfy the HawkScan "Anti-CSRF Tokens" finding on the form-markup side AND make the functional double-submit check pass for a COLD session, using the SAME cookie/header names for both frontends — no per-console fork.
Output: 5 classic forms carry the hidden field; classic `login.js`/`password.js` and Vue `Login.vue`/`PasswordReset.vue`/`store/auth.js` prime the cookie and send the header.

## COLD-SESSION FIX (plan-checker BLOCKER 1)
The console login/reset PAGES are served by static nginx (`location /`, not proxied to Express), so a fresh incognito/cleared-cookie session has NO `XSRF-TOKEN` cookie when it first loads the page — the API's reactive `ensureXsrfCookie` never fired because the page load never hit Express. Under enforce that first protected POST would 403. Fix: every entry page that can issue a protected POST calls `GET /api/csrf-token` (classic base) / `GET /api/v2/csrf-token` (Vue base) on load, which mints the cookie, BEFORE any POST. This plan adds those priming calls.

## VUE PASSWORD-RESET FIX (plan-checker BLOCKER 2 — corrected false premise)
The prior version of this plan wrongly stated "no register/reset POST exists in the Vue console." That is FALSE. `services/console/vue/src/pages/PasswordReset/PasswordReset.vue` (reachable directly via the `/#/password-reset?reset_key=...` email link) calls `store/auth.js`'s `requestPasswordReset` -> `$api.$post('/password/reset', ...)` and `confirmPasswordReset` -> `$api.$post('/password/set', ...)`, which resolve through `api.js`'s `apiPath='/api/v2'` to `POST /api/v2/password/reset` and `POST /api/v2/password/set` — both now server-validated by Plan 21-01. This plan wires the `X-XSRF-TOKEN` header onto those two `$api.$post` calls and primes the cookie on `PasswordReset.vue` mount (the hidden `_csrf` field is moot for a SPA — the header is what matters).

CROSS-REPO NOTE: every file in this plan lives inside the `services/console` git submodule, NOT the parent repo. Commit/push inside the submodule; Plan 21-04 bumps the parent's submodule pointer.

DEVIATION FROM LITERAL CONTEXT TEXT (documented per context-fidelity rules): `21-CONTEXT.md` D-05 describes the Vue change as "configure axios `xsrfCookieName`/`xsrfHeaderName`". The Vue console uses NO axios (confirmed repo-wide; `Login.vue` uses native `fetch()`, `core/api.js` is fetch-based). Tasks 3-4 achieve the IDENTICAL intended outcome (an `X-XSRF-TOKEN` header sourced from the `XSRF-TOKEN` cookie on each protected request) by adding the header directly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Static-nginx-served console page (cold session, no cookie) -> first protected POST | Without the priming GET, a cold session has no XSRF-TOKEN cookie and would 403 under enforce |
| Console JS (trusted origin) -> XSRF-TOKEN cookie read | Legitimate console JS reads the cookie the API issued and echoes it as a header |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-05 | Spoofing (CSRF, client half) | Classic login/register/forget/reset-confirm forms; Vue Login + PasswordReset flows | mitigate | Hidden `_csrf` field satisfies the scanner's form-detection; the `X-XSRF-TOKEN` header (primed via GET /api/(v2/)csrf-token then read from the cookie) is the functional half, enforced server-side by Plan 21-01 across all 7 routes |
| T-21-06 | Denial of Service | Cold/incognito session lockout under enforce | mitigate | Every entry page that can POST primes the cookie on load (BLOCKER 1 fix): classic login.js + password.js on DOM ready, Vue Login.vue + PasswordReset.vue on mount |
| T-21-CC | Tampering (cross-console consistency) | Both consoles' CSRF wiring | mitigate | Both consoles read the SAME `XSRF-TOKEN` cookie, send the SAME `X-XSRF-TOKEN` header, validated by the ONE shared server-side check in Plan 21-01 — no per-frontend fork |

No package-manager installs are part of this plan.
