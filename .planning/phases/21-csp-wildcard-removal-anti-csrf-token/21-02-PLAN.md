## SHARED-SEAM ARCHITECTURE (closes the whack-a-mole permanently)

**Classic console:** a single new file, `services/console/src/assets/thinx/csrf.js`, is included via `<script>` tag on all 3 entry pages (`index.html`, `password.html`, `auth.html`) - the same 3 pages Task 1 already adds hidden `_csrf` fields to. On DOM ready it (a) fires the `GET /api/csrf-token` prime and (b) calls `$.ajaxSetup({ beforeSend: ... })`, which installs a GLOBAL default `beforeSend` hook that jQuery invokes before EVERY subsequent `$.ajax()` call made anywhere on that page - including `login.js`'s 3 calls, `password.js`'s 1 call, and `auth.js`'s 3 calls (row 5's previously-missed `/login` call included), with zero edits to those three files. Any future `$.ajax()` call added to any of these pages inherits the header automatically.

**Vue console:** `core/api.js`'s existing `composeHeaders()` already builds the header object for every `$get`/`$post`/`$put`/`$delete` call made through the shared `Api` class. Adding `X-XSRF-TOKEN` there (Task 4) covers `store/auth.js`'s 2 password-reset/-set calls (rows 10-11) and every other current/future `$api.*` call in the codebase (profile, apikeys, devices, admin, transformers - all harmlessly get the extra header even though they're JWT routes, not CSRF-protected) with zero edit to `store/auth.js`.

The ONLY Vue call sites that need per-site edits are the two that bypass `core/api.js` entirely via raw `fetch()`: `Login.vue` (row 7, already known) and `OAuthReturn.vue` (row 8, newly found). Both are wired individually in Tasks 3-4. If a future Vue page adds a THIRD raw-`fetch()` auth call instead of using `this.$api`, it would need the same manual treatment - this is a known, accepted, and now-narrow residual risk (see threat model T-21-CC2), versus the previous per-call-site whack-a-mole across the ENTIRE codebase.

## COLD-SESSION PRIMING (every entry point, verified independently)

The console login/reset/oauth-return PAGES are served by static nginx (classic: `location /`; Vue: the SPA shell), so a fresh incognito/cleared-cookie session has NO `XSRF-TOKEN` cookie until something explicitly primes it. Under enforce, a cold first protected POST would 403 without priming. This plan primes on every page that can issue a protected POST as a FIRST load (not just via in-app navigation):
- Classic `index.html` (login/register/forget) + `password.html` (reset): the shared `csrf.js` primes fire-and-forget once per page load - safe because a human types into the form before the POST fires (no race).
- Classic `auth.html?g=true` (OAuth/magic-link return): `auth.js`'s `Auth.init()` calls `Auth.login()` -> `POST /login` IMMEDIATELY on DOM ready, in the same tick as the fire-and-forget prime, so the cookie has NOT landed yet -> cold-session 403 under enforce (found by plan-check pass 4, the classic analog of OAuthReturn.vue). FIX: `csrf.js` exposes its prime GET as `window.__csrfReady`; `auth.js`'s auto-login branch does `window.__csrfReady.then(function(){ Auth.login(); })` so the POST only fires after the `XSRF-TOKEN` cookie is set.
- Vue `Login.vue`: primes fire-and-forget on mount (human types username/password before submit - no race).
- Vue `PasswordReset.vue`: reachable directly via `/#/password-reset?reset_key=...` email link - primes independently on mount (human fills the form before submit - no race).
- Vue `OAuthReturn.vue`: reachable directly via the OAuth-provider redirect (`/#/oauth-return?t=...&g=...`) and its `created()` hook calls `complete()` (which POSTs `/login`) IMMEDIATELY with no human-typing delay in between - so its prime MUST be awaited before the POST fires, unlike the other two pages' fire-and-forget prime.

| Boundary | Description |

| Static-nginx-served console page (cold session, no cookie) -> first protected POST | Without priming, a cold session has no XSRF-TOKEN cookie and would 403 under enforce |
