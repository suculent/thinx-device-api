<objective>
Wire the console-side half of the double-submit anti-CSRF token (SEC-CSRF-01) into BOTH consoles living in the `services/console` submodule: the legacy AngularJS/jQuery console (`services/console/src`) and the Vue console (`services/console/vue`). Add the hidden `_csrf` form field the scanner's plugin 20012 inspects to every POST login/account form, and send the real `X-XSRF-TOKEN` header (sourced from the `XSRF-TOKEN` cookie the API now issues, per Plan 21-01) on the login/account XHR calls.

Purpose: satisfy the HawkScan "Anti-CSRF Tokens" finding on the form-markup side AND make the functional double-submit check pass, using the SAME cookie/header names for both frontends — no per-console fork of the mechanism.
Output: 5 forms across 3 classic-console HTML files carry the hidden field; `login.js` and `Login.vue` send the header.

CROSS-REPO NOTE: every file in this plan lives inside the `services/console` git submodule, NOT the parent `thinx-device-api` repo. This plan's changes must be committed and pushed inside the submodule (`services/console`), then Plan 21-04 bumps the submodule pointer in the parent repo as part of the deploy step — do not attempt to commit these paths directly from the parent repo's git index.

DEVIATION FROM LITERAL CONTEXT TEXT (documented per context-fidelity rules): `21-CONTEXT.md`'s D-05 describes the Vue console change as "configure axios `xsrfCookieName`/`xsrfHeaderName`". The Vue console does NOT use axios anywhere (confirmed via repo-wide grep — `Login.vue` calls the browser's native `fetch()` directly, and the `services/console/vue/src/core/api.js` wrapper is also fetch-based, not axios-based). Task 3 below achieves the IDENTICAL outcome the decision intends (an `X-XSRF-TOKEN` header sourced from the `XSRF-TOKEN` cookie sent on the login request) by adding the header directly in the `fetch()` call, since axios's automatic convention has no equivalent to configure.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Console static HTML (served by nginx, no API contact until submit) -> hidden `_csrf` field | Field value is DOM markup only; not itself a security boundary |
| Console JS (trusted origin) -> `XSRF-TOKEN` cookie read | Legitimate console JS reads the cookie the API issued (Plan 21-01) and echoes it as a header |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-05 | Spoofing (CSRF, client half) | Login/register/forget forms (classic), Login.vue (Vue) | mitigate | Hidden `_csrf` field satisfies the scanner's form-based detection; the `X-XSRF-TOKEN` header is the functional half, enforced server-side by Plan 21-01's `verifyCsrfToken` |
| T-21-06 | Tampering | Hidden `_csrf` field value itself | accept | The field alone provides no security value (it is DOM markup an attacker's page cannot read cross-origin, but also cannot itself be validated meaningfully server-side without the cookie); the actual protection is the double-submit cookie/header pair — a cross-origin attacker cannot read the `XSRF-TOKEN` cookie value without XSS, and `SameSite=lax` blocks it from being set via a forged cross-site request |
| T-21-CC | Tampering/Repudiation (cross-console consistency) | Both consoles' CSRF wiring | mitigate | Both consoles read the SAME `XSRF-TOKEN` cookie and send the SAME `X-XSRF-TOKEN` header name, validated by the ONE shared server-side check in Plan 21-01 — no per-frontend fork that could let one console bypass protection |

No package-manager installs are part of this plan.
</threat_model>
