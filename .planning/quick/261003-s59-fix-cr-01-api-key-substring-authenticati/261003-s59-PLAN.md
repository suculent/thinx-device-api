<objective>
Close CR-01 (`.planning/phases/27-influxdb-2-upgrade/27-REVIEW.md`): API-key authentication accepts any substring of a stored key or hash. With that fixed, an empty, 1-char or sliced `Authentication` value no longer authenticates on any entry point: device registration (`lib/thinx/device.js:870`), OTT request (`:1156`), firmware update (`:1269`), and the owner/api_key POST-body middleware (`lib/router.js:185`).

Purpose: owner ids are not secret (they appear in firmware and MQTT topics), so today anyone can authenticate as an owner who has API keys. While planning, I read the code and reproduced two more problems locally with stub Redis. The review's suggested fix alone would not close the bypass on the two device paths the task names:
1. `log_invalid_key` answers success when `is_http` is false, and both `ott_request` and `firmware` pass false. Any wrong key therefore passes there. Task 1 closes this.
2. The guard after `firmware()`'s verify call rejects only when no `ott` is in the body. A request carrying `ott` + `forced: true` gets firmware served with no valid key. Task 2 closes this at the caller.

Caller audit result (the task asked whether any verify caller depends on substring matching):
- `lib/router.js:185` does. It wraps the key in the 36-char UUID sanitizer, so it could only ever match a 36-char slice of a 64-char key or hash. Task 2 normalizes it at the caller with `sanitka.apiKey`; substring matching is not kept.
- The device paths do not. They pass the raw `Authentication` header. The firmware library sends the bare key (`THiNXLib.cpp:489,658`, `Authentication: <key>`), Node trims the header whitespace, and every spec sends exactly `envi.ak` or a full key hash. No prefix or embedded-key caller exists, so no normalization is needed there.
- `rejectLogin` uses the same pattern: a substring search used as an equality check. Exploitability is narrow because the search term is the stored hash, which the server controls. It would matter only if a stored password were empty or short, and every writer stores a sha256 (`lib/thinx/owner.js:644,675`). Task 2 fixes it anyway with the same helper.

Output: one new spec (committed RED first), `Util.safeEqual`, the fixed `lib/thinx/apikey.js`, three caller fixes, and two follow-up todos for related problems this plan does not fix.
