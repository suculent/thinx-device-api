# Quick 261004-22b: OTT redemption serves the firmware binary (+ spec key-log sweep) Summary

**`GET /device/firmware?ott=` answers the raw firmware bytes as `application/octet-stream` again, with Content-Length, x-MD5 and Content-Disposition. Since `fee22323` (2022) it had sent a JSON-wrapped Buffer under the binary's Content-Length, so ESPhttpUpdate could not flash it. Failure answers and all v9x protections are unchanged. Spec files no longer print MQTT keys, API keys, key hashes or reset keys to the CI log.**

- `spec/jasmine/DeviceOttSpec.js`: new describe "OTT redemption binary (quick 261004-22b)" and two helpers, `fetchBytes` (HTTP client, collects Buffers) and `rawGet` (raw `net` socket):

  - B2: reads the raw socket and checks that there is no `"type":"Buffer"`, no `"success"`, no JSON Content-Type, and a body length equal to the Buffer length.

## POST /device/firmware (direct path), reported, not changed

`device.firmware` → `updateFromPath` → `update_binary` → `callback(true, {md5, filesize, payload})` → `Util.respond(res, object)`. This JSON-serializes the whole envelope, with the Buffer as `{"type":"Buffer","data":[...]}`. It is not the fee22323 bug: this path has always used `respond` on the envelope, it sets no binary headers, and no firmware tree calls POST `/device/firmware` (THiNXLib only builds `/device/firmware?ott=`). Per the plan, I left it as is.
