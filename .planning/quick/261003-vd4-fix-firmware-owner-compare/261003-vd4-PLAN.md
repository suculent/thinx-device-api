Close item 5 of `.planning/todos/pending/2026-10-03-device-side-ownership-gaps.md`. `Device#firmware` must load only the device of the owner whose API key it verified.

**Today** (`lib/thinx/device.js` `firmware(req, callback)`, after s59/t29/tv5; line numbers have moved since the todo was written):
- It takes `firmware_owner = sanitka.owner(rbody.owner)` and `udid = sanitka.udid(rbody.udid)` from the body (`rbody` = `body.registration` when present). It requires `mac` and an `Authentication` header, then calls `apikey.verify(firmware_owner, key, false, …)`. Since s59 a failed verify is final, whatever `ott` or `forced` say.
- After verify it opens the raw CouchDB device handle by udid **without comparing `doc.owner`**. Then, for whatever document it got:
  - `deploy.initWithDevice(device)` mkdirps `device.owner`'s deploy dir;
  - `deploy.hasUpdateAvailable(device)` decides availability from that document's owner, `version` and `env_hash`;
  - `device.auto_update` gates the update;
  - `nid:<udid>` is read and, when done, deleted (another owner's notification);
  - the OTT branch calls the OTT entry point.
- The envelope path is the verified owner's (`latestFirmwareEnvelope(firmware_owner, udid)`, `latestFirmwarePath(firmware_owner, udid)`), so another owner's build is never served. However, a verified owner B naming A's udid gets A's document driving the decision. If B still has a deploy dir for that udid (for example a transfer whose best-effort deploy-file move did not complete), B's stale build is served to a request about A's device.
- A malformed or missing udid (sanitka → null) still reaches CouchDB.

**Fix (decision).** In firmware(), replace the raw lookup with `this.fetchOwned(udid, firmware_owner, (owned, device) => …)`, the t29 single ownership check. It answers `(true, doc)` only for a document whose `owner` is exactly `firmware_owner`. A missing, foreign, malformed or erroring lookup gets `(false, "no_such_device")`, and invalid input never reaches CouchDB. When it refuses, firmware() keeps its existing unknown-device answer byte for byte: the `[error] no such device` console line and `callback(false, "no_such_device")`. Everything after the lookup (deploy calls, the MAC fallback, nid reads, the forced/OTT/normal branches) runs unchanged, but only inside the owned branch, so it only ever sees the verified owner's device. The earlier `alog.log(firmware_owner, "Attempt to register device: …")` stays where it is. It writes to the verified owner's audit log, never to A's.

**MAC fallback inside firmware().** firmware() has no `devices_by_mac` lookup. Its only MAC source is `latestFirmwareEnvelope(firmware_owner, udid).mac`, falling back to a local `mac` that is always null (the `typeof (rmac) === "undefined"` guard can never fire, and the normalized value is never used afterwards). After the fix that envelope is the verified owner's, for that owner's own udid. The dead fallback is pre-existing and out of scope. Note it in the SUMMARY; do not change it.

**Key rule (one rule, the same as u86 and v9d).** A device-originated request may act on udid U only when the presented `Authentication` value is exactly a key or key hash in `ak:<doc.owner>`, the store of U's **current** owner (s59 exact constant-time match). How this fits the other tasks:
- u86 moves the key together with the device on transfer. So no other owner holds a key that is valid for U. The previous owner's keys stop working for U the moment the owner changes. There is no cross-owner fallback (u86 left continuity as a todo).
- firmware carries the owner in the body. It verifies `(body owner, key)` first, as since s59. `fetchOwned(U, body owner)` then enforces `body owner === doc.owner`. Together that is exactly "the key verifies for doc.owner".
- addpush (v9d) has no body owner, so it verifies against `doc.owner` directly. The set of accepted keys is the same.
- firmware neither reads nor writes `lastkey`. u86 refreshes it on register check-ins only. Gating firmware on `lastkey` would refuse a re-keyed device until its next registration.
- The CI-only `TEST_ENV_APIKEY` bypass (`ENVIRONMENT=test`) verifies for any owner. `fetchOwned` still binds U to the body owner, so the bypass never crosses owners here.

At execution time, read v9d's and u86's SUMMARYs. If either landed a rule whose accepted set differs (for example v9d also binds `lastkey`), do not bend firmware to match. Keep this rule and record the divergence under "Rule consistency" in the SUMMARY for the operator.

**OTT branch (consistency with 261003-v9x).** v9x owns the OTT entry point (`ott_request`, `storeOTT`, `ott_update`). vd4 does not edit them. vd4 guarantees only that firmware()'s OTT branch is reached after the verify guard and inside the owned branch. It still passes the request on exactly as v9x left it. A verified, owned request therefore hands v9x a body whose owner is the verified owner and whose udid is that owner's device, and that is the input v9x's design expects ("owner from the registration body, verify the key for it, then store the OTT"). firmware() answers exactly what the entry point answers.

If v9x's SUMMARY explicitly hands firmware()'s OTT call over to this task as a follow-up (a changed call shape), apply exactly that hand-off and record it. If v9x's entry point would refuse something firmware()'s body always carries, stop and report the conflict instead of editing v9x's code.

**Response shape, firmware side (read-only check done while planning).** The refusal stays the existing unknown-device answer. `lib/router.deviceapi.js` passes the string to `Util.respond`, which writes the plain body `no_such_device` with HTTP 200. DeviceSpec (07) pins exactly that string. On the device side:
- THiNXLib for ESP8266 (`thinx-firmware-esp8266-pio/lib/THiNX/src/THiNXLib.cpp` and the `-ino` copy, around lines 970-1047 and 1680-1745) never POSTs `/device/firmware`. **What changes for real users** (copy into the SUMMARY and the todo resolution):
