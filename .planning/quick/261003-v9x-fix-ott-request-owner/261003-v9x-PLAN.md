<objective>
Close item 3 of `.planning/todos/pending/2026-10-03-device-side-ownership-gaps.md`: `Device#ott_request` reads the owner from the request object instead of the request body, so the One-Time-Token (OTT) firmware flow always fails closed. Fixing that field reopens the OTT flow in production, so this plan also makes the reopened flow safe: bind every stored token to a verified owner and a device that owner owns, re-check the binding at redemption, replace the guessable token, bound its lifetime, and keep tokens out of the logs.

**What happens today (read from the code, line numbers are pre-sibling and drift; grep by name):**
- `storeOTT(body, cb)` (`lib/thinx/device.js` ~:60) stores `JSON.stringify(body)` (the whole request or registration body) under `ott:<token>`, then sets a 86400 s expiry in a second, unchecked call. The token is the sha256 of `new Date().toString()`, which has one-second resolution: it can be enumerated (~86 400 candidates per day of validity), and two tokens issued in the same second are identical, so the second request overwrites the first record.
- `ott_request(req, cb)` (~:1197) passes `sanitka.owner(<request object>.owner)`, always undefined, to `apikey.verify`, which answers false → `OTT_API_KEY_NOT_VALID`. Reached from `POST /device/firmware` with `body.use == "ott"` (`lib/router.deviceapi.js` ~:40-58) and from inside `device.firmware` (~:1427) when the body carries `ott`. If the owner were read correctly, it would store the raw body with no udid or ownership check.
- `ott_update(ott, cb)` (~:1225) is reached by `GET /device/firmware?ott=` with no other authentication (the token is the bearer). It parses the record (a corrupt record throws inside the Redis callback), then calls `deploy.latestFirmwarePath(record.owner, record.udid)`. That function sanitizes the owner but not the udid, and `Filez.deployPathForDevice` concatenates `<deploy_root>/<owner>/<udid>`, so a record udid like `../<ownerA>/<udidA>` resolves to another owner's build directory.
- **Live cross-owner read through the register path (not only item 3).** `update_device_and_respond` (~:220-300) issues an OTT for auto-update devices with an update available, using `storeOTT(<the registration body>)`. Since tv5, a registration whose body udid is malformed (for example a traversal string) falls back to the owner's own device by MAC and checks in, but the stored record still carries the raw body udid. Owner B, holding only its own key and its own auto-update device with a pending build, can therefore redeem a token that serves owner A's firmware (which can embed environment values such as Wi-Fi credentials). This plan closes it by storing the checked-in binding instead of the body.
- `update_binary` (~:182-215) re-sets the token's expiry to 3600 s on **every** redemption, so a token redeemed at least hourly never expires. `device.firmware`'s forced path passes the body-supplied `ott` value into the same call, so any key holder can re-extend any `ott:` key they know.
- Logs print full tokens: the GET route ("GET request for FW update with OTT: ..."), the POST use=ott response log, the not-found log in `ott_update`, and the `registration_response` info log on the FIRMWARE_UPDATE branch.

**Firmware evidence (read-only, record in SUMMARY and todo):**
- `thinx-firmware-esp8266-ino/lib/thinx-firmware-esp8266/src/THiNXLib.cpp` (same code in `thinx-firmware-esp8266-pio/lib/THiNX/src/THiNXLib.cpp`): the registration parser's `status == "FIRMWARE_UPDATE"` branch (~:970-1045) reads `registration["ott"]` and sets `deferred_update_url = "/device/firmware?ott=" + ott`; `update_and_reboot` (~:1666-1730) fetches it with `ESPhttpUpdate.update` on port 7443 (HTTPS) or 7442 (HTTP when `forceHTTP`/`__DISABLE_HTTPS__`); `loop()` (~:2174-2180) calls `update_and_reboot(deferred_update_url)` again on every iteration, and nothing clears `deferred_update_url` after `HTTP_UPDATE_FAILED`. The MQTT update branch (~:825-829) also reads `update["ott"]`.
- No firmware tree sends `use: "ott"`; `POST /device/firmware` use=ott has no known firmware caller. Only the register-path token and the GET redemption are used by shipping firmware.
- `thinx-firmware-esp32-pio/lib/thinx-firmware-esp32/` is empty (library not checked out), so there is no ESP32 evidence.
- **Pre-existing, not fixed here:** since `fee22323` (2022-04-27, "responder fixes") the GET success branch calls `Util.responder(res, response.payload)` with two arguments, which serializes `{"success":{"type":"Buffer","data":[...]}}` as JSON (Content-Type overwritten to JSON, Content-Length still the binary size) instead of the binary `Util.respond` used to send. So OTT redemption has not delivered a flashable image since 2022, and a device with a pending update retries in a tight loop. Fixing it would resume OTA for every auto-update device with a pending build (a fleet-wide, hard-to-reverse change), so it is recorded as a new todo for an operator decision. This plan leaves that line and its headers unchanged.

**Decisions:**
1. **Owner and key.** The owner comes from the request body (unwrapped from `body.registration` when present, the same unwrap `device.firmware` does). The key in the `Authentication` header must verify for that owner with `APIKey#verify`, which is exact and fails closed since s59.
2. **One rule for device-originated requests.** A request is authorized when the presented key verifies (exact) for the owner AND the device is owned by that owner (`Device#fetchOwned` / `Device.isOwnedBy`, t29). This is the rule register check-in (tv5, u86) and `device.firmware` apply, and the one the todo prescribes for `/device/addpush`. The key does NOT also have to be the device's own key (`lastkey`): u86 records `lastkey` at check-in but does not enforce it, and enforcing it only here would make OTT stricter than the firmware path it duplicates. A per-device-key rule would have to cover register, firmware, addpush and OTT at once, so it is noted as a follow-up and not introduced here. **Consistency check at execution:** read `.planning/quick/261003-v9d-fix-device-addpush-key-check/261003-v9d-PLAN.md` (and its SUMMARY / landed `device.push` code if present). If v9d landed a shared helper for exactly this rule, call it instead of open-coding. If v9d landed a different (stricter) rule, apply that same helper here so there is one rule, and record the deviation in the SUMMARY.
3. **What is stored.** A record of exactly `{owner, udid}`: the verified owner and the owned document's udid (ott_request), or the checked-in device's owner and udid (register path). Nothing else from the request is persisted. Today the whole body sits in Redis for 24 h, including push token, location and environment hashes.
4. **Redemption re-validates.** The token must be 64 lowercase hex characters before Redis is touched. The record must parse, its owner and udid must pass sanitka, and the udid must still be owned by that owner, so a transfer or revoke after issuance kills the token. A failing record is deleted. Tokens issued before deploy (full-body records) keep working when their owner/udid are valid and owned, so in-flight updates are not broken.
5. **Token properties.** 32 random bytes (`crypto`, already imported), hex-encoded, the same 64-char shape as before, so firmware URLs are unchanged. One `SET ... EX 86400` (the legacy-client form `lib/thinx/git.js` ~:502 already uses). Lifetime: 24 h unredeemed (unchanged), then at most 3600 s after the first redemption, never extended. The cap uses TTL-then-EXPIRE, so it works on any Redis version; a failure is logged and the redemption proceeds. **Not strict one-time:** shipping THiNXLib re-requests the same URL after a failed download, and the original design comment says "valid for 60 minutes after first use". A replay within the window only re-serves the same owner's firmware for the same udid, which any key holder of that owner can already fetch with `POST /device/firmware` forced. Strict one-time redemption is recorded in the new todo, to do together with firmware-side retry handling.
6. **Vocabulary (existing strings reused).** Issuance: `OTT_API_KEY_NOT_VALID` (owner/key), `no_such_device` (device; "not yours" answers like "not found", the t29 rule), new `OTT_BINDING_INVALID` / `OTT_STORE_FAILED` (storeOTT). Redemption: `OTT_UPDATE_NOT_FOUND` (malformed, unknown or Redis error; the ZZ `?ott=foo` cases depend on this exact string), `OTT_INFO_NOT_FOUND` (bad record or lost ownership), `OTT_UPDATE_NOT_AVAILABLE` (no build).

**Out of scope (left open):** todo items 2 (addpush, v9d), 4 (messenger), 5 (`device.firmware` compare). The GET serialization defect, strict one-time redemption and the plaintext port 7442 go to the new todo. Not touched: `package.json` scripts, `.circleci/config.yml`, `Dockerfile.test`, `docker-entrypoint.sh`, `thinx-core.js`, `lib/thinx/deployment.js`, and the `/device/register` and `/device/addpush` handlers in `lib/router.deviceapi.js`.
