**Decision: B. Remove the two HTTP tail routes.** Evidence, verified during planning:
- **No client calls them.**
  - The classic console defines a wrapper `tailBuildLog` (`services/console/src/app/js/thinx-api.js:157-158` export, `:1315-1325` body) and nothing calls it. A grep for `tailBuildLog` across `services/console` (excluding node_modules/dist) finds only those three lines.
  - The Vue console (`services/console/vue/src`) has no reference to the tail route, the logtail message or WebSocket at all.
  - Firmware, docs (`docs/APIs.md` lists audit/build/list/build only), builders and the worker have no reference.
  - Repo-wide, the only references outside `.planning` are `thinx-core.js:581,585` and two specs.
- **The console tails over the WebSocket.** `LogviewController.js:98-108` sends `{logtail: {owner_id, build_id}}` over `$rootScope.wss` (the owner connection). That path is handled at `thinx-core.js:598-614`.
- **The routes never worked and they leak.**
  - `thinx-core.js:382` binds `router` to the return value of `lib/router.js`, which is undefined. So `logTailImpl` (`:575-579`) throws a TypeError and answers 500; even on success it never responds.
  - The routes are registered inside the per-connection function (`:573-589`), which the connection handler calls on EVERY WebSocket connection (`:693`). Before the first connection after boot, both paths answer 404 (`spec/jasmine/00-AppSpec.js:117` pins that). After it, they answer 500. Each connection pushes two more layers onto the express 5.2.1 router for the life of the process.
- **No spec depends on them working.**
  - `spec/jasmine/ZZ-AppSession.js:74` expects 200, but that file does not match the `jasmine/*[sS]pec.js` glob in `spec/support/jasmine.json`, so it never runs.
  - `00-AppSpec` expects 404, which removal keeps.
  - `CsrfRouteInventorySpec` and the runbook have no rows for these routes; only the historical `25-RESEARCH.md` mentions them.
- Option A (keep and fix) would add an authenticated endpoint that duplicates the WebSocket message with no caller. That is new surface for nothing.

**WebSocket path audit:** same defect class, so it is included. `initSocket` (`thinx-core.js:591-629`) and the connection handler (`:646-694`):
1. **Socket owner is unverified.** The owner is the first URL path segment (`:662`). The only checks are cookie-header substrings: `x-thx-core` at upgrade (`:503`), `x-thx` at connection (`:667`). `sessionParser` already runs at upgrade (`:498`), so `request.session` is available, but `request.session.owner` is never compared with the path.
2. **The logtail owner comes from the message.** `object.logtail.owner_id` (`:601`) is passed straight to `blog.logtail` (`:613`).
3. **`Buildlog#logtail` reads unowned.** It uses the unowned `Buildlog#fetch` (`lib/thinx/buildlog.js:528`), sends the record's first message, and builds the tail path from the MESSAGE owner plus the record's udid (`:568-569`). If that path is missing, it creates it with `mkdirp` and writes a world-writable `build.log` (`:573-588`). So anyone with a cookie containing `x-thx-core` can tail any owner's build log by naming that owner and build id, or create directories and files under any owner id they name. This is exactly the class `router.logs.js` closed with `Buildlog#fetchOwned` (26-02 #2).
4. **The log-socket registry is keyed by a client-chosen value.** `app._ws[logsocket]` (`:687`) uses the second path segment, a client-chosen value, as a global key. A colliding key from another connection redirects the stream that `:611` looks up.
5. **`init` trusts the message owner.** `object.init` (`:617-627`) initializes the messenger for the owner named in the message.
6. **Crash: an unauthenticated remote DoS.** `JSON.parse(message)` (`:596`) runs with no try/catch in the `ws` 'message' listener. There is no `uncaughtException` handler anywhere (grep of `thinx.js`, `thinx-core.js`, `lib/`). Reproduced during planning with `ws` 8.21.3 on node: one non-JSON frame on an accepted socket kills the process (`SyntaxError ... at Receiver._write`). Frames like `null` or `{"logtail":null}` throw a TypeError the same way. Today any client whose Cookie header contains `x-thx-core` (any value) gets that listener.

**Not fixed here (todo):** `Messenger` is a process-wide singleton (`thinx-core.js:155`). `initWithOwner` stores ONE `this._socket` (`lib/thinx/messenger.js:901`), and every notification path sends to it (`:279, :328, :499, :557` and `sendWithValidSocket` callers `:409-441`). So device notifications reach whichever owner's socket sent `init` last. Binding `init` to the verified owner does not change that, so it goes to a new pending todo (Task 3).

**Approach** (Claude's discretion, recorded for the SUMMARY):
- Extract the WebSocket session handling into `lib/thinx/socket_session.js`, so it is testable without booting thinx-core (Redis, CouchDB, `/mnt/data/conf`).
- The gate sits in the connection handler, after the handshake. Unverified sockets are closed with 1008 rather than refused at upgrade. Reason: `spec/jasmine/ZZ-WebSocketHandshakeRtmSpec.js` opens cookieless sockets and only waits for 'open', and `ZZ-WebSocketLifecycleSpec.js` uses a bogus `x-thx-core` cookie and observes `socketMap` cleanup. Both CI specs stay green unchanged. The upgrade handler is not touched.
- The logtail output is always the connection the frame arrived on. The classic console sends every logtail over the owner connection, where today's lookup already falls back to that connection, so its behaviour is unchanged.
- Log-connection registry keys become `<owner>/<id>`. That removes the cross-owner overwrite, and `app._ws["__proto__"]` can no longer be assigned through the path.
- Not-found frame: `Buildlog.LOGTAIL_NOT_FOUND = "Sorry, no log records fetched."`. This reuses the wording of the existing, never-reached no-websocket branch. The classic console appends any non-notification frame to the log view, so the user sees that line.
