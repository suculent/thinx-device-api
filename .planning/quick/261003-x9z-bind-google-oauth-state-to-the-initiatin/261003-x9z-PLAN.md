# Quick 261003-x9z: bind Google OAuth state to the initiating browser

<objective>
Close the login-CSRF gap found while triaging pentest findings XALG-3/XALG-4 (2026-10-03).

**Triage context (record in SUMMARY):**
- XALG-3 (GitHub) as reported is a false positive: `?return=` is allowlisted (`oauth_return.js` normalize + `allowedOrigins`, live probe with `return=https://evil.com` sets no `thx_oauth_origin` cookie), and GitHub `state` is already bound to the browser via the `thx_oauth_state` cookie (`lib/thinx/oauth-github.js` login/callback, `statesMatch`). Starting an OAuth login is not a privileged state change; SameSite=Strict would drop the cookie on the IdP's top-level redirect back, so Lax is correct.
- XALG-4 (Google) as reported is also wrong in its reasoning (the quoted `thx_oauth_state` Set-Cookie is the GitHub response pasted twice; live Google init sets no cookie at all), BUT the real gap is adjacent: Google `state` is a server-wide Redis marker (`consumeOAuthState` in `lib/router.google.js`) not tied to any browser. An attacker starts a Google login, completes it with their own Google account, stops before following the callback, and hands the victim `https://rtm.thinx.cloud/api/oauth/google/callback?code=…&state=…`. The marker is valid and unconsumed, so the victim is logged into the attacker's account (classic login CSRF, CWE-352).
</objective>
