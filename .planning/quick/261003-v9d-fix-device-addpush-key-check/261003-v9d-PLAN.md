Close item 2 of `.planning/todos/pending/2026-10-03-device-side-ownership-gaps.md` (threat T-t29-09, transferred again as T-tv5-09). Today, anyone holding any well-formed key-shaped string can set the push token of any udid.

**Today:**
- The `/device/addpush` handler in `lib/router.deviceapi.js` checks the body and the push token format. It runs the `Authentication` header through `sanitka.apiKey` (format only; missing or malformed → 403) and passes `req.body` to `device.push`.
- `Device#push` in `lib/thinx/device.js`:
  - logs the whole request body, push token included;
  - never verifies the key;
  - looks the device up by the body udid; a malformed udid becomes `null` and still reaches CouchDB;
  - writes `push` onto whatever document it finds;
  - answers `push_token_registered` even when the write fails.

**What does the client send? (evidence, recorded while planning; copy into the SUMMARY)**
- The only server caller of `device.push` is the router. A repo-wide grep (excluding node_modules) finds `addpush` in only four places: the router, `spec/jasmine/ZZ-RouterDeviceAPISpec.js`, a comment list in `docs/APIs.md`, and `thinx-api-openapi.yaml`.
- THiNXLib never calls addpush. Its copies are `thinx-firmware-esp8266-ino/lib/thinx-firmware-esp8266/src/THiNXLib.cpp`, `thinx-firmware-esp8266-pio/lib/THiNX/src/THiNXLib.cpp` and the `spec/test_repositories/thinx-firmware-esp8266` submodule. All of them only POST `/device/register` (Authentication header, `registration.owner`) and GET `/device/firmware?ott=`. None sends a push field. `thinx-firmware-esp32-pio/lib/thinx-firmware-esp32` is an empty submodule directory in this checkout, so it gives no evidence either way.
- A public GitHub code search for `"device/addpush"` (default branches only) finds only this server: `suculent/thinx-device-api` and its mirror `thinx-cloud/thinx` (router, spec, docs, OpenAPI). No firmware and no mobile app use it. Private repositories are unknown.
- The token formats `sanitka.pushToken` accepts (64-hex APNs, FCM) point at a mobile client that never shipped.
- Nothing in the server reads `device.push`. The FCM collection in `lib/thinx/notifier.js` is commented out. The bug corrupts a stored field and lets anyone trigger CouchDB writes; it delivers nothing to anyone.
- The OpenAPI entry documents only `push`. The udid is required in practice but undocumented, and no owner field exists.
- **So no client names an owner on addpush. Owner field (decision):** the request must name the owner in a top-level `owner` field. That is the field name THiNXLib uses in `registration.owner` and the one `device.firmware` reads from its body. The rule is literally "verify against the owner the request names", and it is the device check-in rule.

**The rule (decision, same as check-in after tv5/u86).** A push token is written only when all of these hold:
1. The body names an owner. `reg.owner` must be a string accepted by `sanitka.owner`. Absent or null counts as not named and is refused.
2. `this.apikey.verify(owner, api_key, true, …)` succeeds. Since s59 this is an exact, constant-time match on an entry's `.key` or `.hash`, and it fails closed.
3. `this.fetchOwned(udid, owner, …)` answers `(true, doc)`. This is t29's check: a malformed udid never reaches CouchDB, ownership uses strict `Device.isOwnedBy`, and lookup errors fail closed.

Then `this.edit({udid, push})` writes the `push` field and nothing else.
- This is exactly what `/device/register` requires: verify the key for the body owner, then act only on that owner's device (tv5 `resolveRegistration`).
- `fetchOwned` is reused as-is, because the owner is known before the lookup.

**No lastkey binding (decision).**
- Check-in accepts any key of the owner and never compares it with the device's `lastkey`. Quick 261003-u86 makes check-in *record* `lastkey = sha256(<presented key>)`.
- Requiring the device's own key here would make addpush stricter than check-in, which is the operation that re-issues the device's MQTT credential. It would also break after every re-key until the next check-in, and fail for devices with no `lastkey` or a legacy one (substring-era values, masked builder keys, the CI test key).
- addpush also never *writes* `lastkey`. Check-in stays its only writer, so u86's transfer key identification ("the key the device last checked in with") is unaffected.
- After a u86 transfer, the device document and its key both belong to the recipient. A request naming the recipient works.

**No transfer continuity on addpush (decision; u86 revision of 22:39).** The revised u86 plan adds an optional 5th argument to `APIKey#verify`: a device context (`{udid, currentOwner}`, built by a new Device helper).
- With that context, a failed verify for a *previous* owner redirects to the device's current owner when the key's `transfer` binding names that udid and owner: `callback(true, "transfer_redirect", current_owner)`.
- A direct success for the new owner *consumes* the binding.
- u86 applies the context only to `register` and `firmware`, and lists `/device/addpush` as not covered.

This plan keeps it that way: `push()` calls `verify` with exactly four arguments and never builds a device context.
- Consumption is defined by the operator as "after re-registration with the new owner the old path stops". If addpush passed the context, then a push-token call naming the new owner would consume the binding. That would cut off the old-owner check-in path of a device that has not re-registered yet.
- No firmware calls addpush, so continuity on this endpoint would serve no client.
- Result: a request naming the sender after a transfer is refused with `authentication`, where register would redirect it. A request naming the current owner works directly.
- Existing 4-argument callers are untouched by u86 by design, so this holds whether or not u86 has landed when this plan executes.
- Record this in the todo Resolution.

**Answers (decision).** All are sent through `Util.responder`: HTTP 200 + `{"success":false,"response":<reason>}`. That is the device-API failure convention (register, firmware), and the existing ZZ cases "(jwt, invalid)" and "(jwt, valid)" pin 200.
- **`push_device_not_found`** covers every udid failure *after* authentication: malformed, absent or non-string udid, unknown udid, another owner's udid, lookup error.
  - It is this endpoint's existing answer for an unknown udid. A foreign udid now gets exactly what a nonexistent one gets, so the endpoint is no udid-existence oracle.
  - Both the foreign and the unknown case do the same work (one verify, one `devicelib.get` inside `fetchOwned`).
  - `fetchOwned`'s own reason (`no_such_device`, used on the console routes since t29) is mapped to this string. Changing the endpoint's established not-found answer would gain nothing.
- **`authentication`** covers an absent or empty key, an absent or invalid owner, and a key that does not verify for the named owner.
  - It is the endpoint's existing reason for a missing key.
  - It is decided before any device lookup and depends only on (owner, key), so it cannot reveal anything about a udid.
  - Verify's internal messages (`owner_found_but_no_key` / `apikey_not_found`) are collapsed into it, so they reveal nothing about whether an owner has keys.
- **`push_token_not_registered`** means the write itself failed. Before, that case answered success.
- **Unchanged:** the router's 403 for a missing or malformed Authentication header (pinned by the noauth ZZ case and the OpenAPI 403), `no_body`, `no_token`, `no_push_info`, `invalid_type_*`, and success `push_token_registered`.

**Log hygiene.** The first log line in `push`, which prints the whole request body including the push token, is replaced. The new line names only the sanitized udid. Refusal lines name a short reason category and the udid only, never the key, the push token or the body.

**Who is affected in production** (copy into the SUMMARY and the todo Resolution):
- (a) A caller writing the push token of a device that is not its key owner's. It is refused. Nothing consumed that field, so no delivery changes.
- (b) A caller that names no owner, which is every request shape documented or tested so far. It now gets `authentication`. No known client exists (evidence above). If one appears, it must add `owner`, its key's owner id.
- (c) The owner's key plus `owner` plus its own udid: unchanged success. A failed write now answers `push_token_not_registered`.
- **Pre-deploy, read-only (operator, optional):** on the node running the `thinx_api` task (placement floats; use node-local `docker logs`, not `docker service logs`), count only. Never print matching lines: they contain push tokens and bodies.
  - `• Push Registration` lines show whether anything calls addpush at all.
  - Of those, lines containing `"owner":` show whether that client already names an owner.
- **Post-deploy:** count `[push] refused` lines.
