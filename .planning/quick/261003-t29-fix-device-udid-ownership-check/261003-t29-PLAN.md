<objective>
Close the udid IDOR (BOLA) on the console/API device routes. This is threat T-skk-09, recorded by quick 261003-skk as todo `.planning/todos/pending/2026-10-03-device-udid-routes-missing-owner-check.md`. Before this fix, any logged-in user, or any API-key caller once skk lands, who knows another owner's udid could do all of the following:
- read that device's document, including the unmasked Wi-Fi `environment` (POST /api/device/detail, POST /api/v2/device, POST /api/device/envs)
- rewrite any field of it, including `owner`, because the CouchDB `modify` update handler copies every field (`design/design_devices.json`)
- attach their own repository to it, which creates directories in the victim's deploy path
- detach its source
- add a readwrite MQTT ACL topic in their own namespace to it (mesh attach)
- offer it in a device transfer. Accepting that transfer rewrites the device owner, which is a full takeover

Udids are not secret: they appear in MQTT topics, transfer e-mails, firmware and logs.

Purpose: one shared ownership check, used by every udid-keyed entry point, that answers "not yours" exactly like "not found".

Response decision: HTTP 200 with `{"success":false,"response":"no_such_device"}`, sent through `Util.responder`, for missing, foreign, malformed-after-presence-checks and CouchDB-error cases alike. Reasons, in order:
1. It is already the answer of the only owner-checked udid path in the codebase. `device.run_transformers` answers `no_such_device` for both a missing and a foreign device, and `ZZ-RouterTransformerSpec` pins that text. All udid routes therefore end up with one not-found answer.
2. The legacy API reports not-found as HTTP 200 with `success:false`, and both consoles branch on `success` inside their success handlers. A 404 would route these calls into jQuery/axios error paths.
3. A CI case asserts status 200 on a gated route with a udid that has no device (`ZZ-RouterBuilderSpec` "POST /api/v2/build (JWT, valid) V" attaches `envi.dynamic.udid` and expects 200). A 404 would break it.

Existence is not leaked through the body, the status or the work done: one `devicelib.get` for both the foreign and the missing case.

Design: the check lives in the library and the routers delegate to it. The library signatures of `device.edit/detail/envs` and `devices.attach/detach/attachMesh/detachMesh/revoke` stay unchanged, because `DeviceSpec`, `DevicesSpec`, `TransferSpec` and `messenger.js` call them directly.
- `lib/thinx/device.js` gains three things:
  - `Device.isOwnedBy(doc, owner)`: strict `===` on a string owner.
  - `Device#fetchOwned(udid, owner, cb)`: answers `(true, doc)`, or `(false, "no_such_device")` with no oracle.
  - `Device#filterOwned(owner, udids, cb)`: one `devices_by_owner` view query; answers with the owned subset.
- `lib/router.device.js` gains `withOwnedDevice(req, res, udid, onOwned)`. Every udid-keyed handler runs through it after its existing presence checks, with the owner from `Util.ownerFromRequest(req)`: the session owner, else the API-key owner that `lib/router.js` verified (quick 261003-skk). It is never a body owner.
- `lib/thinx/transfer.js` uses the same two methods for the batch request, the accept filter and a re-check before ownership changes.
