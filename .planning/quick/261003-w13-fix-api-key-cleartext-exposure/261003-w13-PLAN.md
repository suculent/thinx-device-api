## Decision A: the hash stays in the list (residual, recorded)

`APIKey#verify` / `key_in_keys` accept an exact `.hash` with the same power as the `.key` (s59). Devices in the field authenticate with it: `lastkey = sha256(hash)` is a supported case in u86 and vep. The `hash` the list keeps returning is therefore itself a working credential.

It stays for now:
- Both consoles need it to revoke keys and to link devices to keys (device `keyhash`).
- The instruction keeps console-facing shapes, except for the removed secret field.
- Replacing it requires a console change (submodule) plus a non-credential fingerprint, or retiring hash authentication after a device audit.

This is recorded as item 1 of the residual todo, with both paths. `name` reveals the key's last 34 hex characters. After vep's random keys, 120 bits stay unknown and an exact match is required (s59), so `name` stays as it is (vep's VEP list pins it).

## Decision B: Redis keeps storing the cleartext key (not dropped; recorded)

Dropping `.key` from `ak:<owner>` is not safe today:
1. The owner's Default MQTT API Key is the owner's Mosquitto password (`add_mqtt_credentials(owner, key)`). The API presents it when it connects as the owner (messenger). The server must be able to read it back.
2. The stored `.hash` is itself a working credential (Decision A). A hash-only store still holds a cleartext credential for every key, so it gains nothing until hash authentication is retired.
3. vep's builder and MQTT registration hand a device its own credential: the pre-image of `lastkey`, which is `.key` for devices that authenticate with the key. Without `.key` those devices would get `""` or the hash.
4. The migration is one-way: it deletes key material, and no rollback exists.

Prerequisites, recorded in the residual todo:
- retire hash authentication (field audit of devices whose `lastkey` equals sha256(entry.hash));
- verify by constant-time sha256(presented) == stored hash;
- move the owner's broker password to its own secret, or keep `.key` only on the Default MQTT entry;
- decide vep's embed rule for key-presenting devices;
- then a one-way migration with an operator-approved backup.

## Decision C: build-tree files are not removed (recorded with evidence)

- **Removing them before or while the worker builds breaks the build.** `services/worker/builder` copies `./thinx_build.json` into the NodeMCU/Mongoose firmware filesystem (~:813, ~:905) and compiles the generated `thinx.h` (~:958, ~:1084).
- **The API has no hook after a successful remote build** (the production path). `cleanupSecrets` runs only on refused builds, failed builds and after a local build exits (builder.js ~:451, ~:567, ~:584, ~:821, ~:1122, ~:1136, ~:1228). The worker's completion detection is a known Phase 23 gap. An API-side removal could only cover failed builds.
- **The credential ships inside the outputs by design.**
  - The firmware binary compiles `THINX_API_KEY` in, and NodeMCU/Mongoose images carry `thinx_build.json`.
  - Several worker branches zip the whole work dir (`zip -rq … ./*`, ~:663, ~:689, ~:693).
  - Deleting the build-tree copies would not remove it from the deploy zip or the OTA payload. OTA serves the deploy firmware, not the build tree.
- **The header's name is platform-specific** (`thinx.h`, `thinx.json`, `boot.py`, `config.lua`, `conf5.json` in `platforms/*/descriptor.json`). For MicroPython/NodeMCU/Mongoose it is the project's own entry or config file, which the builder rewrites in place, not a separate secrets file.
- **Exposure:**
  - the build tree is not served over HTTP;
  - the zip is served only to the owner (`lib/router.build.js` session + owner check);
  - Redis holds every key in cleartext in the same trust domain;
  - since vep the value is the device's own credential or `""`.
- **Disposition:** T-w13-07 accepts this. The worker-side cleanup after zipping, and excluding the files from `./*` zips, are residual todo items for the worker submodule.
- A partial API-side removal of `thinx_build.json` on failed builds was rejected. It would leave the identical value in the header, and it would invalidate vep's VEP builder harness, which reads that file after the build answered.

## What changes for operators and API clients

1. `GET /api/user/apikey/list` and `GET /api/v2/apikey` no longer carry `key`. Both consoles are unaffected (evidence above). A third-party client that read `key` from the list must keep the key it received at creation.
2. The create routes still answer `{api_key, hash}` once. The API log no longer prints the new key or hash.
3. Owner MQTT credentials:
   - Logging in as an owner that has keys but no Default MQTT API Key now creates one, instead of hanging.
   - The MQTT credential registered for a newly created Default key is that key.
   - An unreadable key store no longer triggers a create attempt.
4. No data migration, no console change, no push or deploy. Commits may be unsigned under the operator's standing GPG exception.
