# Quick 261003-w13: API key cleartext exposure Summary

The console's API key list (`GET /api/user/apikey/list`, `GET /api/v2/apikey`) now answers `{name, hash, alias}` only. The create routes show a new key once and log only the alias, the owner and a 6-character hash prefix. The owner's MQTT broker password is read from the key store through `APIKey#get_owner_mqtt_apikey`. `Owner#mqtt_key` and `create_default_mqtt_apikey` answer exactly once, reuse an existing Default MQTT key, and register the key they created.

## Additional item: create_default_mqtt_apikey callback arity (own TDD pair)

- **Bug.** `APIKey#list` calls back with one argument, but `create_default_mqtt_apikey` read it as `(err, body)`. `body` was always undefined, so an existing Default key was never found. Since vep refuses duplicate aliases, `Owner#create` then failed with `creating_mqtt_api_key_failed` for an owner whose `ak:` store survived.
- **RED (`d3c3214e`), `OwnerDefaultMqttKeySpec`:** 4 specs, 3 failures. The two reuse cases and the `Owner#create` survivor case failed. The control case (no Default key, so one is created) passed.
- **Fix (`155764f7`):** the callback reads the single argument and skips non-objects and entries without a string alias. Result: 4 specs, 0 failures.
- **Other callers checked.** I grepped every `apikey.list(` caller: `router.apikey.js` listAPIKeys, `Owner#mqtt_key`, `APIKey#get_first_apikey`, and the ApikeySpec/BuilderApiKeySpec cases. All of them already used one argument. `list()`'s signature is unchanged.
- **Superseded in Task 1.** Both Owner methods now read the store accessor instead of `list()`. OwnerDefaultMqttKeySpec stays green on the accessor.

## Decisions as implemented

- **A. The list keeps `hash`.** It is still a credential that `key_in_keys` accepts, but both consoles need it to revoke keys and to link devices to keys. The path to remove it is item 1 of the residual todo.
- **B. Redis keeps `.key`.** The owner's broker password must stay readable, the stored hash is itself a credential, and vep's builder embeds `.key`. The prerequisites and the one-way migration are item 3 of the residual todo.
- **C. Build-tree files are not removed.** The worker needs them during the build, and the credential is compiled into the firmware and zipped by design. Worker-side follow-ups are item 5 of the residual todo.
- **Default-key rule.** `get_owner_mqtt_apikey` uses `APIKey.isOwnerMqttKey`: the alias contains "Default MQTT API Key". The arity fix and the old `create_default_mqtt_apikey` matched only an alias that starts with that text. That is the same set for every alias the API writes; transfers refuse to move the Default key.

## Operator- and client-facing changes (not pushed or deployed)

1. **Breaking API change.** `GET /api/user/apikey/list` and `GET /api/v2/apikey` items lose the `key` property. They are now exactly `{name, hash, alias}`, with the same values and order as before. Both consoles are unaffected; I re-checked them with grep in the submodule. A third-party client that read `key` from the list must keep the key it received at creation.
2. The create routes still answer `{api_key, hash}` once. The API log no longer prints either value.
3. Owner MQTT credentials:
   - Logging in as an owner that has keys but no Default key now creates one; before, the request hung.
   - A newly created Default key is the one registered with Mosquitto; before, the store's first entry was.
   - An unreadable or malformed store no longer triggers a create.
   - Sign-up for an owner whose `ak:` store survived reuses the existing Default key; before, it failed.
4. No data migration, no console change, no push.
