<objective>
Bind `POST /device/register` to the owner whose API key authenticated it. This implements the operator decision, verbatim intent: "/device/register, when it falls back to matching by MAC, should check in as a device of the api key's owner."

It closes item 1 of `.planning/todos/pending/2026-10-03-device-side-ownership-gaps.md`, threat T-t29-09, which quick 261003-t29 transferred.

**Today** (`lib/thinx/device.js` `register`, the `devicelib.get` block and the `devices_by_mac` callback, ~lines 966-1004):
- Udid branch: checks in only when the stored owner loosely equals the registration owner. Otherwise it falls through.
- MAC fallback: queries `devices_by_mac` and, when the view returns more than one row, checks in as `rows[0]` whatever its owner. `checkinExistingDevice` → `authorize_mqtt(api_key, device)` then stores the caller's API key as that device's MQTT password and refreshes its ACL topics under the victim owner's namespace (`/<A>/<udid>`, `/<A>/shared/#`, `/<A>/<mesh>`). It also writes the caller's version/firmware/status/push/location onto A's document and answers with A's udid, owner id, alias and mesh ids. The firmware library saves `registration.owner/alias/udid` from an "OK" response (`thinx-firmware-esp8266-ino/lib/thinx-firmware-esp8266/src/THiNXLib.cpp` ~:937-945).
- Off-by-one: the more-than-one-row check is a regression from commit `0d30f36f` (2022-03-21, #304). Before it, any non-empty result reattached. Since then a single same-owner match has created a duplicate device on every no-udid registration.
- Foreign body udid: when the body udid names another owner's device and the MAC finds nothing usable, the new-device branch runs with that foreign udid. `authorize_mqtt` overwrites the foreign device's MQTT password with the caller's key *before* `devicelib.insert` fails with a 409 conflict.
- Malformed body udid: becomes `null`, so the document id, MQTT username and ACL key are all `null`/`"null"`.

**Owner source.** `registration_owner = sanitka.owner(reg.owner)`, and `this.apikey.verify(registration_owner, api_key, true, …)` must succeed before any lookup. Since quick 261003-s59 that match is exact and constant-time and fails closed. So `registration_owner` *is* the verified key owner. There is no other owner source in this path, and the plan adds none.

**Decisions** (Claude's discretion, recorded for the SUMMARY):
1. **MAC fallback is owner-scoped.**
   - Rows of `devices_by_mac` (key = `this.normalizedMAC(reg.mac)`, exactly the key used today) are filtered in memory with `Device.isOwnedBy(doc, registration_owner)`, the t29 strict-equality helper. Each row's `doc` is used, else its `value`. Rows whose `udid` fails `sanitka.udid` are also dropped.
   - When ≥1 owned row remains, the registration checks in as the first one in view order. CouchDB orders equal keys by document id, so the choice is deterministic. This is the same `rows[0]` rule as today, restricted to the owner, and it restores the pre-2022 "any match reattaches" semantics.
   - When none remains, it proceeds as a normal new-device registration for the key owner.
   - Rows of other owners are ignored. One info line gives their count. It never prints their udids, owners or documents.
2. **Udid path, same rule.** Only a valid body udid (`sanitka.udid`) is considered. It is looked up with `devicelib.get`:
   - owned by the key owner → check in as today
   - CouchDB 404 (absent, or deleted by a revoke) → keep it as the new device's udid (today's behaviour; `DeviceSpec` (02) depends on it, because it creates `envi.udid` this way)
   - a document of another owner, or any other lookup error → discard it, log one info line naming only the requested udid, and use a fresh `uuidV1()`
   - Either way, the owner-scoped MAC step runs next.

   A malformed or absent udid starts from a fresh `uuidV1()`.

   Rationale: keep the device's udid only when it is proven to be the owner's or proven free. Never let an unverifiable udid reach `authorize_mqtt` or `insert`.
3. **No new CouchDB view.** Audit of the views:

   | View (`design/design_devices.json`) | Emits | Used by register |
   |---|---|---|
   | `devices_by_mac` | `(doc.mac, doc)` for docs with a truthy mac | MAC fallback; owner filter applied in memory (rows are bounded by MAC collisions, typically 0-2) |
   | `devices_by_owner` | `(doc.owner, doc)` | no. It would load every device of the owner on every no-udid registration |
   | `devices_by_udid` | `(doc.udid, doc)` | no. register reads by `_id` (`_id === udid`) |

   No owner+MAC view exists. Adding one would not even reach production: `lib/thinx/database.js` (~:228) inserts `_design/devices` create-only at boot, and only `_design/paging` is rev-aware upserted. It would also rebuild every view in that design doc. An in-memory filter is enough.
4. **MAC normalisation unchanged.** Lookup and storage both go through `normalizedMAC` (upper-case; a 12-hex string gains colons), so a device always matches its own stored value. Known pre-existing limitation, not changed: a dash-separated 17-character MAC is upper-cased but keeps its dashes, so it never matches the colon form.
5. **Response for firmware.**
   - A new device answers the existing new-device shape: `{registration: {success: true, owner: <key owner>, alias, udid: <fresh or kept>, iv, status: "OK", meshes, timestamp}}`.
   - A check-in answers the existing check-in shape with the owned device's udid.
   - THiNXLib adopts `owner`, `alias` and `udid` on "OK", so firmware keeps working and takes over the new udid.
6. **`authorize_mqtt` stays where it is** (before `insert` on the new-device branch). Moving it after the insert would delay the credential write that the firmware's immediate MQTT connect races against. Because the udid reaching it is now always owned, proven free or freshly minted, the remaining window is the get-404 → insert TOCTOU. That is accepted (T-tv5-07).

**Who is affected in production** (the executor copies this list into the SUMMARY):
- (a) A device that registers without its own known udid (first boot, factory reset, reflash without `thinx.json`, or a malformed/foreign udid), whose MAC appears on ≥2 documents where the first by doc id belongs to another owner. **Today:** it checks in as that other owner's device (MQTT takeover, document overwrite, foreign owner/udid in the response). **After:** it registers as a new device of its own key owner, or reattaches to its own owner's device with that MAC.
- (b) A device whose stored udid now belongs to another owner, for example after a transfer while it still carries the old owner's key, or a cloned config image. **Today:** "Insert failed", after overwriting that udid's MQTT password with its key. **After:** a new device of its key owner with a fresh udid, which it adopts.
- (c) A device of an owner that has exactly one device with the same MAC and presents no/absent/malformed/foreign udid. **Today:** a new duplicate device per such registration (since 2022). **After:** it reattaches to the existing device and keeps that device's udid, alias, source, mesh ids, transformers and environment. Boards with a factory-default or cloned MAC under one owner now collapse onto one record instead of creating a second one first.
- (d) A malformed body udid. **Today:** a document with `udid: null` and MQTT username "null". **After:** a fresh udid.
- (e) Unchanged: the steady-state check-in of a device presenting its own udid, which is the vast majority of traffic.
