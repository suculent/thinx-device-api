# Quick 261003-u86: Device transfer carries its API key Summary

**Accepting a transfer now moves the device's API key entry from the sender's `ak:` store to
the recipient's in one atomic Redis EVAL compare-and-swap, together with the owner change.
Shared, unidentifiable, ambiguous and Default-MQTT keys are refused at request and again at
accept. A transferred device that still presents the sender's owner id keeps registering and
fetching firmware as the recipient's device. The binding that makes this work is never
consumed (operator decision 3).**

## Operator decisions applied

1. **Default MQTT API Key:** the transfer is refused with `apikey_owner_mqtt_key`.
2. **Continuity is seamless and is part of this task** (Task 3).
3. **No consumption (overrides the plan).** The transfer binding is not removed when the
   device registers with its new owner id. It stays until the key is revoked, the owner is
   purged, or the device is transferred again. A chained transfer of the same udid appends
   the previous owner to `from` and never lists the new owner. Applied as follows:
   - `APIKey#verify` has no consumption step. A direct match behaves exactly as before.
   - Spec case 28 (local) and the last CI continuity case are inverted: after a registration
     with the new owner id, the old triple still redirects to the new owner.
   - The leftovers todo has no reboot/consumption trade-off item.
   - Rationale (operator): EEPROM builds, and builds that pass an owner id to the `THiNX`
     constructor, return to the old owner id at every reboot. The redirect grants nothing
     the key does not already grant, because the key verifies for the current owner directly.

## What changes for real users

1. **The key moves with the device.**
   - Accepting a transfer moves the device's API key (same value and hash) from the
     sender's API-key list to the recipient's.
   - The sender can no longer use, list or revoke it. Anything else the sender ran with that
     key stops authenticating.
   - `mig_apikeys` in the request body is ignored.
2. **New refusals.** In test/dev the answer is HTTP 200 `{"success":false,"response":"<reason>"}`.
   In production, `transferResultRedirect` sends `error.html?success=failed&reason=<reason>`.
   A refused accept leaves the transfer pending.
3. **Shared keys and Default MQTT keys can no longer be transferred.** A fleet that shares one
   key, or a device on the Default MQTT API Key, needs its own key first: create a key,
   reprovision the device, and let it check in once. The check-in records the new key.
4. **Transferred devices keep working.**
   - A `/device/register` or `/device/firmware` request that presents the sender's owner id,
     the moved key and the device's own udid is answered as the recipient's device.
   - The OK registration answer carries the recipient's owner id, which THiNXLib adopts.
   - SPIFFS builds that do not pass an owner to the constructor switch permanently.
   - EEPROM builds, and builds that pass an owner to the constructor, keep presenting the
     sender's id after every reboot. They keep working through the redirect, because it is
     never consumed.
   - While a device uses the sender's id, it is on `/<sender>/<udid>` MQTT topics, so server
     publishes to `/<recipient>/<udid>` are missed (leftovers todo item 3).
5. **Check-ins refresh `lastkey`.** A verified check-in now writes
   `sha256(<presented key>)`. Before, `lastkey` was written only at first registration.
6. **Transfers pending before the deploy are checked at accept. Self-transfers are unchanged.**

## New reason codes

| Reason | Where | Meaning |
|---|---|---|
| `apikey_shared` | request, accept | another device of any owner, or another device of the same request, uses the key |
| `apikey_not_identified` | request, accept | no `lastkey`, no matching entry in the sender's store, or a masked/test key |
| `apikey_ambiguous` | request, accept | more than one entry matches `lastkey` |
| `apikey_owner_mqtt_key` | request, accept | the key is the sender's Default MQTT API Key |
| `apikey_check_failed` | request, accept | the key store GET, its JSON, the owner view or the `_find` failed |
| `apikey_move_failed` | accept | the swap was refused 3 times, a transport error left it unmoved or inconsistent, or the recipient already holds that key/hash |
| `device_move_failed` | accept | the owner write failed (and had not landed); the key was moved back |

Ownership refusals (`no_such_device`) still come first.

## Continuity design as implemented (no consumption)

- **Binding.** `moveDeviceKey` writes `transfer: {udid, from: [owner ids], at: <ISO>}` onto
  the moved entry, inside the same EVAL that moves it. The device document gets
  `transferred_at` (same ISO value) next to `previous_owner`. `APIKey#list` exports only
  name/key/hash/alias, so the binding never reaches the console.
- **Lookup.** Only on a failed verify, and only when the caller passed a device context with
  a valid udid:
  1. `devicelib.get(udid)` gives the current owner;
  2. GET `ak:<current owner>`;
  3. pure `APIKey.findTransferBinding(entries, key, udid, presented_owner)`.
  That is one CouchDB get plus one Redis GET per qualifying failed attempt.
- **Answer.** `callback(true, "transfer_redirect", current_owner)` replaces `statsLog` and
  `log_invalid_key`, so the sender's audit log and stats never see the device. Only the
  current owner's audit log gets "Device <udid> authenticated with a previous owner id".
- **Conditions (all required).**
  - Verify failed for the presented owner. A key the sender still holds verifies as the
    sender first and never redirects.
  - The presented udid is valid. MAC-only registrations never redirect.
  - The udid's document is owned by a `sanitka.owner`-valid owner other than the presented one.
  - That owner's store has exactly one entry whose `.key` or `.hash` `Util.safeEqual`s the
    presented key.
  - That entry's binding names this udid and lists the presented owner (strict equality).
  - Any Redis or CouchDB error answers the unchanged failure (fail closed).
- **Lifetime.** There is no expiry and no consumption. The binding ends when the key is
  revoked, the owner is purged (`ak:` DEL), or the device is transferred again (the binding
  is merged, not duplicated).
- **Covered device paths:** `Device#register` swaps `registration_owner` and `reg.owner`
  before `deploy.initWithOwner` and tv5's `resolveRegistration`. `Device#firmware` swaps
  `firmware_owner` before its audit line, the device lookup and `deploy.latestFirmwarePath`.
- **Not covered:**
  - `ott_request`: `req.owner` is undefined for every caller (device-side todo item 3).
  - `/device/addpush`: it never verifies a key (item 2).
  - MQTT: device credentials are udid/key, and they do not change.
- **Unchanged:** `lib/router.deviceapi.js`, every 4-argument `verify` caller (router body
  `api_key`, the s59 firmware-guard stub), and the test-env bypass.

## Firmware facts (from the plan, unchanged)

- THiNXLib (esp8266 ino and pio) adopts `registration.owner` on a `status: "OK"` answer and
  calls `save_device_info()`.
- On SPIFFS builds that writes `/thinx.cfg`. On EEPROM builds it writes the global
  `json_info` buffer, so the new owner is not persisted (pre-existing bug).
- Boot order: the build-time constant, then the restored owner, then the constructor
  argument, which wins when it is longer than 4 characters.
- esp32 is unverified, because its library submodule is not checked out.
- `FIRMWARE_UPDATE` answers do not carry the owner. That is why `/device/firmware` is covered.

## Recommended read-only audit (operator, before deploy)

Counts only. Never print keys, hashes or `lastkey` values. Over every device document and
its owner's `ak:<owner>` store, count:

1. devices without `lastkey`. Each one would be refused with `apikey_not_identified` until
   it checks in once after the deploy;
2. devices whose `lastkey` matches no entry of their owner's store (none of `sha256(key)`,
   `hash`, `sha256(hash)`). These include devices transferred before this change, which
   still use the sender's key;
3. keys referenced by two or more devices (any owner). Those devices are refused with
   `apikey_shared`;
4. devices on their owner's Default MQTT API Key (`apikey_owner_mqtt_key`).

## Accomplishments

- One atomic Redis step moves the key entry and its binding. The device owner follows, with
  compensation, so the key is never in both stores or in neither, and the device always ends
  on the same side as its key.
- The request gate refuses before anything is stored or mailed. Accept re-checks every device
  right before it moves, one device at a time.
- Continuity for transferred devices on register and firmware, with no audit or stats leak
  to the sender.
- `lastkey` now means what its name says. The transformer job masks it on a copy instead of
  deleting it from the document being saved.

## Deviations from Plan

### Operator-directed

- **No consumption** (decision 3). The plan's verify consumption block, the "consumed" spec
  case and the "refused after consumption" CI step were not built. Local case 28 and the
  final CI continuity case assert that the redirect still works. The threat-model row
  T-u86-08 changes from "mitigate by consumption" to "accept": the residual is nothing beyond
  what the key itself grants. T-u86-12 (devices refused after reboot) no longer applies.

### Auto-fixed / adjusted

**1. [Rule 3 - Blocking] The CI re-key case does not decline its transfer via the GET link**
- **Found during:** Task 3 (ZZ case (b))
- **Issue:** `Transfer#decline` answers its callback twice for a live transfer:
  `storeRemainingKeys` answers, then `callback(true, "decline_completed")` runs as well. Over
  HTTP, the second answer throws "headers already sent" inside the Redis callback. The legacy
  client's promise then calls the same callback again with an error, which throws on
  `JSON.parse`, so the process gets an unhandled rejection. A spec that triggers it would
  fail the run.
- **Fix:** the re-key case asserts the request succeeds and leaves that transfer pending. The
  dt: record is harmless in CI's ephemeral Redis, and the cleanup case revokes the device.
  The bug is recorded as leftovers todo item 6 and as WINDOWS ledger entry #5. It is not
  fixed (out of scope).
- **Files:** `spec/jasmine/ZZ-RouterTransferSpec.js`, `.planning/todos/pending/2026-10-03-transfer-continuity-leftovers.md`
- **Commit:** `16bde50a`

**2. [Harness] Spec numbering and fault injection.** The new DeviceRegisterOwnerSpec cases
are numbered 18-29, continuing tv5's 1-17. The plan's case (7) "CouchDB get error on UDID_B"
binds the moved key to tv5's existing `UDID_BROKEN` (its `get` already errors), so the fake
needed no new fault switch. `AuditStub.log` now records owner ids, and `DeploymentStub` gained
a static `envelope` (undefined by default, `{}` only in the firmware case, because
`Device#firmware` dereferences the envelope) and a recording `latestFirmwarePath`. No existing
assertion changed.

**3. [Rule 2] Extra fail-closed checks.**
- `transferRedirect` also requires `sanitka.owner(current) === current`, and catches a
  throwing `currentOwner`.
- `restoreDeviceKey` re-reads after a refused or errored exact swap, and reports "restored"
  when the stores already hold the pre-move values (a lost reply). Only then does it move the
  entry back.
- In the move-back (`strip`) mode the Default-MQTT check is skipped, so an entry that was
  moved can always go back.
- The firmware CI-guard behaviour (s59) is unchanged.

**Total deviations:** 1 operator-directed redesign, 1 blocking workaround, 2 harness/hardening
adjustments. No scope creep.
