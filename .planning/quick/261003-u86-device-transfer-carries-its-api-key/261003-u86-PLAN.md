<objective>
Implement two operator requirements.

1. Verbatim: "When transferring a device, api key must be transferred with it. If the key is used by multiple devices, transfer must be blocked."
2. The operator decision "Make it seamless in this task": a transferred device that still stores the sender's owner id keeps working, with no reprovisioning.

Operator decisions relayed by the orchestrator:
- (1) the sender's Default MQTT API Key is refused (`apikey_owner_mqtt_key`);
- (2) continuity is folded into this plan.

**Today** (`lib/thinx/transfer.js`, after quick tasks s59/skk/t29/tv5) **the key never moves.**
- `migrate_owned_device` fires an un-awaited `Device#edit` and moves the deploy files.
- It calls the legacy key-migration function only when the body flag `api_keys` is true. The request defaults a different flag (`mig_apikeys`), so this never happens.
- Even when it is called, that function is broken:
  - it compares `sha256(<whole entry object>)` with `dev.lastkey`, so it never matches;
  - it crashes when the recipient has no `ak:` record;
  - it writes both stores with two independent `redis.set` calls.
- Nothing checks whether other devices share the key.

**How a device's key is identified (decision).**
- Device documents carry `lastkey = sha256(<Authentication header>)`. It is written at first registration and never refreshed.
- Since s59 the header must equal an entry's `.key` or `.hash` exactly, so `lastkey` is either `sha256(key)` (== `entry.hash`) or `sha256(hash)`. The ZZ fixture device sends the hash.
- Entry E is the device's key iff `lastkey` `Util.safeEqual`s one of `APIKey.deviceKeyCandidates(E)` = {`sha256(E.key)`, `E.hash`, `sha256(E.hash)`} (non-empty strings, deduplicated).
  - exactly one matching entry in `ak:<sender>` → identified;
  - none → `apikey_not_identified`;
  - several → `apikey_ambiguous`.
- Masked builder keys (todo `2026-10-03-builder-embeds-masked-api-key.md`) and the CI-only `TEST_ENV_APIKEY` match no entry → `apikey_not_identified`. There is no suffix matching, so CR-01 is preserved.
- Task 3 refreshes `lastkey` at every verified check-in, so the field means what its name says. The transformer-job masking deletes `lastkey` from the very object being saved, so it moves to a copy. Otherwise re-keying the other device of a shared pair could never lift the refusal.

**Who else can reference a key (decision).**
- Devices transferred before this change kept the sender's key while `doc.owner` became the recipient. So "used by another device" is checked across all owners.
- It is one CouchDB Mango `_find` per check: selector `{"lastkey": {"$in": <candidates>}}`, fields `_id`/`udid`, `limit` = number of checked devices + 1. Any extra device is then guaranteed to be returned.
- No design-doc change: a new view would rebuild every `_design/devices` index on deploy.
- Devices of the same request that share one key are refused too. That is the literal reading of the rule, and it fails closed.

**Default MQTT API Key (operator-confirmed).** The entry whose alias contains "Default MQTT API Key" is refused (`apikey_owner_mqtt_key`), using the same `indexOf` rule as `Owner#mqtt_key` in `lib/thinx/owner.js`. Reasons:
- it is also the owner's MQTT broker credential;
- `/api/login` hangs in `mqtt_key` once it is gone and other keys remain.

**Atomicity (decision).**
- The node-redis v5 legacy client multiplexes one connection, so `WATCH` is unsafe.
- Every `ak:` write in this plan is one `EVAL` of a multi-key compare-and-swap Lua script, issued through `this.redis.sendCommand`. The legacy client flattens array args and pops the trailing callback (`node_modules/@redis/client/dist/lib/client/legacy-mode.js`).
- The script, with n = #KEYS (1 or 2 here):
  1. GET every `KEYS[i]` (absent reads as the empty string);
  2. return 0 unless each equals `ARGV[i]`;
  3. otherwise write `ARGV[n+i]` to each key (empty means DEL) and return 1.
- JSON is built in JS with `JSON.stringify`, the format `save_apikeys` writes, so `[]` never turns into Lua cjson's `{}`. EVAL is enabled (`services/redis/redis.conf`, `lua-time-limit 5000`).

**Order inside a migration (decision): key first, then owner.**
1. Per-device gate (read-only).
2. `moveDeviceKey`: atomic; most refusals happen here, before anything is written.
3. Awaited `Device#edit` with owner, previous_owner and `transferred_at`.
4. The existing best-effort file and sources moves.

Failure modes:
- (a) Swap mismatch: re-read and retry (3 attempts in total), then `apikey_move_failed`.
- (b) Swap transport error: re-read both stores.
  - Entry only at the recipient → it moved.
  - Entry only at the sender → `apikey_move_failed`.
  - Otherwise → `apikey_move_failed` plus a critical log line.
- (c) Owner write fails: re-read the device.
  - Owned by the recipient → the write landed; keep it.
  - Otherwise `restoreDeviceKey` swaps both stores back to the exact pre-move strings. If that is refused, the entry moves back by `lastkey` with its binding stripped. Answer `device_move_failed`.
- (d) Move-back also fails: critical line plus audit entries for both owners. The key stays with the recipient and the device with the sender: still exactly one store, and the operator reconciles it.

Accept processes devices one at a time.

**Recipient side.**
- The entry keeps `key`, `hash` and all other fields.
- On an identical alias the moved entry's alias becomes `<alias> (transferred <first 8 chars of udid>)`.
- If the recipient already holds the same key or hash → `apikey_move_failed`.

**Continuity design (decisions).**

*Binding.*
- `moveDeviceKey` writes `transfer: {udid, from: [owner ids], at: <ISO>}` onto the moved entry, inside the same EVAL that moves it. The binding is therefore atomic with the move, and it disappears with the key on revoke, owner purge or consumption.
- `from` accumulates across chained transfers while unconsumed. Moving an entry whose binding names the same udid appends the new previous owner; the entry's new owner is never listed.
- `APIKey#list` exports only name/key/hash/alias, so the binding never reaches the console.
- The device document gets `transferred_at` (same ISO value) next to the existing `previous_owner` for audit.

*Lookup, O(1).* Only on a failed verify with a valid presented udid:
1. `devicelib.get(udid)` → current owner;
2. GET `ak:<current owner>`;
3. pure `APIKey.findTransferBinding(entries, key, udid, presented_owner)`.

*Placement.*
- An optional 5th argument to `APIKey#verify`, `{udid, currentOwner(udid, cb)}`, built by `Device#deviceKeyContext(udid)`.
- When the redirect matches it answers `callback(true, "transfer_redirect", current_owner)`. That happens *before* `log_invalid_key`/`statsLog`, so the sender's audit log and stats never see the device.
- When it does not match, the existing failure path runs unchanged (same strings, same audit line).
- Existing 4-argument callers are untouched, including the router body api_key path and the s59 firmware-guard stub, which ignores the 5th argument.
- `lib/router.deviceapi.js` needs no change.

*Covered device paths.*
- `Device#register`: its verify callback swaps `registration_owner` and `reg.owner` before tv5's `resolveRegistration`, which then checks in the bound udid as its current owner. The answer is the normal check-in answer (`owner` = current owner, `status: "OK"` unless an update is pending).
- `Device#firmware`: it swaps `firmware_owner`, so deploy paths and audit use the current owner.

*Not covered.*
- `ott_request`: `req.owner` is undefined for every caller today (item 3 of `2026-10-03-device-side-ownership-gaps.md`).
- `/device/addpush`: it never verifies a key (item 2).
- MQTT: device credentials are udid/key and unchanged.

*Consumption* ("after re-registration with the new owner the old path stops"). When verify succeeds *directly* for the presented owner, the context udid is valid, and the exactly matched entry's binding names that udid, the `transfer` field is removed:
- one single-key EVAL compare-and-swap, up to 3 attempts;
- a failure is logged and never fails the verify.

From then on, the old-owner triple is refused.

*Expiry: none, deliberately.*
- The redirect grants nothing beyond what holding the key already grants: `verify(<current owner>, key)` succeeds directly.
- A time limit would strand devices that are offline longer than the limit.
- The binding ends on consumption, on revoke of the key, or when the device is transferred onward (merged, not duplicated).

*Security conditions, all required.*
- verify failed for the presented owner. A key the sender still holds verifies as the sender first and never redirects.
- The udid is valid; MAC-only never redirects.
- Its document is owned by a different owner.
- That owner's store has exactly one entry that `Util.safeEqual`s the key.
- That entry's binding names this udid (strict) and lists the presented owner (strict).
- Any Redis or CouchDB error fails closed with the existing failure answer.
- Owner ids from the document go through `sanitka.owner`.

**Firmware facts (from `thinx-firmware-esp8266-ino` and `thinx-firmware-esp8266-pio` `THiNXLib.cpp`; the esp32 library submodule is not checked out, so esp32 is unverified).**
- A registration answer with `status: "OK"` makes the library adopt `registration.owner` (and alias/udid) in memory and call `save_device_info()` (~:930-968).
- On SPIFFS builds that writes owner/apikey/udid/alias to `/thinx.cfg`.
- On EEPROM builds the save writes the global `json_info` buffer, not the document it just built, so the new owner is NOT persisted. This is a pre-existing firmware bug.
- Boot order is `import_build_time_constants()` (THINX_OWNER), then `restore_device_info()` (the saved owner wins), then the constructor's owner argument, which wins again when longer than 4 chars (~:163-207).
  - The esp8266-ino example calls `THiNX(apikey)`, so the saved owner sticks and continuity is permanent.
  - The esp8266-pio and esp32 examples call `THiNX(apikey, owner)`, so the compiled sender id is re-applied at every boot.
- `FIRMWARE_UPDATE` answers do not carry the owner. That is why `/device/firmware` is covered too, and the next OK registration delivers the owner.
- The library re-registers periodically within one uptime (`checkin_interval`), using its in-memory owner.

**Consequence the operator should know.** Take a device whose build re-applies the sender id at boot, or an EEPROM build.
1. It presents the recipient's id on its next in-session check-in, which consumes the binding as the operator constraint requires.
2. After its next reboot it presents the sender's id again, and that is refused.
3. Such devices need a rebuild or reprovision for the recipient.

The alternative is to drop consumption and keep the binding for the key's lifetime, which is one guarded block in `verify`. The security cost of that alternative is nil, because the key alone already authenticates as the recipient. This plan implements the operator constraint as stated, and records the trade-off in the leftovers todo and the SUMMARY.

**What changes for real users** (copy into the SUMMARY):
1. **The key moves with the device.**
   - Accepting a transfer moves the device's API key (same value and hash) from the sender's API-key list to the recipient's.
   - The sender can no longer use, list or revoke it. Anything else the sender ran with that key stops authenticating.
   - `mig_apikeys` is ignored.
2. **New refusals and how they are answered.**
   - Request and accept: `apikey_shared`, `apikey_not_identified`, `apikey_ambiguous`, `apikey_owner_mqtt_key`, `apikey_check_failed`.
   - Accept only: `apikey_move_failed`, `device_move_failed`.
   - In test/dev the answer is HTTP 200 `{"success":false,"response":"<reason>"}`. In production `transferResultRedirect` sends `error.html?success=failed&reason=<reason>`.
   - A refused accept leaves the transfer pending.
3. **Shared keys and default MQTT keys can no longer be transferred.** Fleets sharing one key, and devices on the Default MQTT API Key, need their own key first: create a key, reprovision the device, let it check in once.
4. **Transferred devices keep working.**
   - The next registration or firmware request with the sender's owner id, the moved key and the device's own udid is answered as the recipient's device, and the OK answer delivers the recipient's owner id.
   - On SPIFFS builds that do not pass an owner to the constructor, the switch is permanent.
   - Other builds: see the consequence above.
   - Until the device adopts the new id it uses `/<sender>/<udid>` MQTT topics, so server-pushed messages published to `/<recipient>/<udid>` are missed. This is in the leftovers todo.
5. **Check-ins refresh `lastkey`.**
6. **Pending transfers created before the deploy are checked at accept. Self-transfers are unchanged.**

**Data migration:** none.

  - `APIKey#key_in_keys` matches `.key` or `.hash` exactly (`Util.safeEqual`).
  - `APIKey#list` exports only name/key/hash/alias.
- **Default MQTT key.** `lib/thinx/owner.js` `Owner#mqtt_key` picks the first entry whose alias contains "Default MQTT API Key" (constant `DEFAULT_MQTT_APIKEY_ALIAS` in apikey.js).
- **Device lookups.**
  - `Device#fetchOwned(udid, owner, cb)` answers `(true, doc)` or `(false, "no_such_device")`.
  - `Device#filterOwned(owner, udids, cb)` answers an udid array (one `devices_by_owner` view).

- **Redis client.** Production and every CI client is the legacy wrapper (`thinx-core.js` `redis_store_client.legacy()`; TransferSpec `redis_base.legacy()`). It provides `sendCommand(...args, cb)`, and an integer reply is a JS number.
