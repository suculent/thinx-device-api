# Phase 43 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Surface.** One surface only: the toastr toasts of the Legacy AngularJS console (`rtm.thinx.cloud`), rendered by
`parseNotification` in `services/console/src/app/js/controllers/LogviewController.js`. The Vue console is not touched
(D-02: it opens no WebSocket and renders no device notification text). There is no new screen, no new component and
no new style.

**Shape of the work.** The Legacy side of this phase is already written: the escaped toast is console commit `e43a94d`
(an ancestor of the pinned `cfff199`), tested by `services/console/src/test/toast-escape.cjs`. The one-off legacy
build ships that and nothing else (D-14), so **this phase makes no further change to `services/console/src`**. The
rest of the phase is API work (NOTIF-02 multi-tab sockets, NOTIF-03 build status frames). That work changes which
toasts arrive and how many, and the parts of this contract that are not already true today are API-side rules about
the frames (see "Build Status frame rules").

**Sources.** CONTEXT.md D-01..D-16 (locked); `LogviewController.js` at `cfff199`; `toast-escape.cjs`;
`lib/thinx/builder.js` (`notify` :177, `wsOK` :92, `processExitData` :520, `processShellData` :541, the remote-worker
guard :284-298); toastr 2.1.3 (`assets/thinx/js/plugins/toastr/`); Metronic `assets/global/css/plugins.css` :423-441;
`assets/thinx/css/custom.css` :886-914.

## Copywriting Contract

The toast copy comes from the API frames and does not change in this phase (D-11: frame format unchanged). The Legacy
console keys its build refresh on the exact bodies `Pulling repository`, `Building...` and `Completed`
(`LogviewController.js` :212-216), so those three strings are frozen.

| Element | Copy |
|---------|------|
| Primary CTA | None new. The build is started by the existing Legacy "Build" action; this phase only delivers its status toasts |
| Build toast title | `Build Status` (all build frames) |
| Build progress bodies | `Pulling repository` -> `Building...` (type `success`) |
| Build success body | `Completed` (type `success`), exactly once per successful build |
| Build failure / refusal bodies | The existing reason codes, type `error`: `invalid_device`, `invalid_build_arguments`, `worker_secret_missing`, `worker_busy`, `Failed`, `error_platform_unknown`, `error_starting_build`, `device_mac_missing`, the MCU-mismatch message, `ERROR: worker needs a connected socket for remote builds`, and the worker's exit `status` when it is not `OK` |
| Rendered body form | The non-actionable toast renders `thinxEscapeHtml(JSON.stringify(msg.body))`, so a string body shows **with its JSON double quotes**: `"Completed"`. This is today's rendering and is accepted as is (no Legacy change in this phase) |
| Empty state heading | Not applicable: toasts have no empty state. With no frame, nothing is shown |
| Empty state body | Not applicable |
| Error state | A build failure is one red toast titled `Build Status` whose body is the reason code. The next step is the build log, which the user opens from the device row as today. No green toast may follow it (rule F-2) |
| Device status toast | Title `Device Status Update`, body the escaped JSON of `msg.body` (8 s). Unchanged; `forwardNonNotification` status and generic toasts stay off (D-15) |
| Actionable toast (NOTIF-01) | Title = escaped `msg.title`; body = escaped `msg.body`, then the validated `nid`; buttons `Yes` / `No` (`response_type: "bool"`, info toast) or an input plus `Send` (`response_type: "string"`, warning toast). A frame whose `nid` fails `^[A-Za-z0-9_-]{1,128}$` shows no toast at all |
| Destructive confirmation | None: this phase adds no destructive action |

### Escaped-text rendering (NOTIF-01, already implemented)

- Every device-supplied field (`body`, `title`, `nid`, and `JSON.stringify(body)`) is escaped (`& < > " ' \``) or
  validated before it is placed in toastr markup, ids or selectors. A body such as
  `<img src=x onerror=alert(1)><b>hi</b>` renders as that literal text, with no image, no bold and no script.
- Toast type comes only from the allow-list `info|success|warning|error`. Any other `type` (except `actionable`) shows
  no toast.
- Proof: `npm run test:toast` in `services/console/src` passes, and the served
  `https://rtm.thinx.cloud/.../LogviewController.js` contains `thinxEscapeHtml` (D-04).

### Build Status frame rules (NOTIF-03, API side: `lib/thinx/builder.js`, `lib/thinx/queue.js`)

Before this phase no build frame reached a console (`notifiers.websocket` was never filled), so the duplicate and
mis-typed frames in `builder.js` were invisible. Routing them through `messenger.sendToOwner` (D-09) makes every one of
them a toast in every open tab. The frame shape stays as in D-11; these rules decide **which** frames are sent:

- **F-1 One terminal toast per build.** A successful build produces exactly one `Completed` frame. Today the success
  path can emit up to three (`notify("Completed")` :555, `wsOK` :557, and `wsOK` again from `processExitData` :530),
  plus an `"OK"` frame from `notify(data.status)` :526. The planner picks the mechanism (for example: `wsOK` stops
  sending a second frame where `notify` already sent `Completed`, and `notify` does not send a bare `OK` body).
- **F-2 Failure is never green.** A build that ends in failure produces an `error` frame with its reason and **no**
  `Completed`/`success` frame after it. Today `processExitData` always calls `wsOK` (green `Completed`) even when the
  exit status is a failure, and the remote-worker guard (:291-297) passes the string `"error"` as `success_status`,
  which `successStringFromBool` turns into `success`. Both must produce `error`.
- **F-3 Terminal frame carries `build_id`.** The terminal `Completed` frame has the D-11 shape including `build_id`
  (`buildNotification`), because the console stores `msg.build_id` in the device's build record (:219-227). The
  `wsOK`-only shape without `build_id` is not used for the frame that reaches consoles.
- **F-4 No log lines on the notification socket.** Raw build log lines (`processShellData`) are not sent to the owner's
  sockets (D-10). A tab without the log overlay open shows no log text; the overlay of the tab that asked for the
  logtail keeps working through its own socket.
- **F-5 Owner only.** Each frame reaches only the build owner's sockets (D-12; quick 261003-vn3 invariant).

Proof: a builder/messenger spec counts the frames that `sendToOwner` receives for one successful build (one
`Completed`, no `OK`, all types `success`) and for one failed build (one `error`, no `Completed`), and checks that owner
B's socket receives nothing (D-12).

## Interaction Contract

### Toast behaviour (as rendered today, unchanged)

| Toast | toastr method | Timeout | Dismiss | Extras |
|-------|---------------|---------|---------|--------|
| Build Status (and any non-actionable titled frame) | `msg.type` (`success` / `error` / `info`) | 20 000 ms, `extendedTimeOut: 0` | close button, click | progress bar; fade out 300 ms |
| Device Status Update | `msg.type` | 8 000 ms | close button, click | progress bar |
| Actionable `bool` | `info` | none (`timeOut: 0`) | close button only (`tapToDismiss: false`) | Yes / No buttons; a click collapses the buttons and emits `submitNotificationResponse` |
| Actionable `string` | `warning` | none | close button only | text input and Send |

Toasts stack top-right, newest on top, with no de-duplication. A successful build therefore shows three toasts in
sequence in each open tab: `"Pulling repository"`, `"Building..."`, `"Completed"`. Each stays for 20 s unless closed.
`Pulling repository`, `Building...` and `Completed` also trigger the device list and build history refresh
(`updateDevices`, `updateBuildHistory`) in that tab.

### Multi-tab behaviour (NOTIF-02)

- Each Legacy tab opens two sockets: `/<owner>` (notifications; it sends `{init: owner}`, which subscribes it to the
  messenger) and `/<owner>/<timestamp>` (log). Only the `/<owner>` socket is subscribed, so **each tab shows each
  frame exactly once**.
- With two tabs open on the same owner, both connect without an upgrade refusal, and each tab shows its own copy of
  every owner frame (build status, actionable, device status). Toasts are independent per tab: closing or answering a
  toast in one tab does not close it in the other. There is no cross-tab sync and no Legacy change to add one.
- Closing one tab leaves the other tab receiving (D-05: each socket's close releases only itself).
- Per-owner socket cap (D-07, value is the planner's call): the cap counts sockets, and every Legacy tab holds two, so
  the cap must admit at least 2 tabs (4 sockets). Recommended: 10 sockets, about 5 tabs. A refused upgrade is invisible
  in the Legacy UI (`wss.onclose` is a no-op): that tab simply gets no toasts. The server logs one line per refusal.
  No toast, banner or copy is added for it.
- Another owner's tabs receive nothing (D-08, D-12).

## UI Considerations

Probe: `ui-consideration-probe.cjs` over 3 elements (E1 actionable toast, E2 Build Status toast stack, E3 owner tabs/sockets),
19 applicable categories, 0 unclassified. Resolved in autonomous mode: 16 explicit, 3 backstop, 0 dismissed; plus 3
pre-existing Legacy defects kept unresolved (accepted, no Legacy change allowed by D-14).

**Explicit (truths):**
- E1 loading: The actionable toast appears only when its frame arrives; there is no pending state (toastr renders synchronously).
- E1 error: An actionable frame whose `nid` fails `^[A-Za-z0-9_-]{1,128}$`, or a non-actionable frame whose `type` is not info/success/warning/error, shows no toast (`npm run test:toast`).
- E1 overflow: A long device-supplied body wraps inside the toast; no markup is rendered.
- E1 long-text: A device-supplied `notification.body` or `title` containing HTML renders as literal escaped text in the actionable toast (`thinxEscapeHtml`, `npm run test:toast` passes).
- E2 empty: Owner B's sockets receive zero Build Status frames for owner A's build, including queued builds (D-12, F-5).
- E2 loading: Progress frames `Pulling repository` and `Building...` arrive as `info`/`success` Build Status frames before the terminal frame.
- E2 error: A failed or refused build delivers an `error` frame with its reason and no `Completed`/`success` frame after it; the remote-worker guard frame is type `error` (F-2).
- E2 populated: A successful build delivers exactly one `Completed` frame of type `success`, carrying `build_id`, and no `"OK"` frame (F-1, F-3).
- E2 partial: A build that ends without a terminal status sends no `Completed` frame (F-1/F-2: `Completed` only on success).
- E2 overflow: No raw build log line is sent through `sendToOwner`; only status frames are (F-4, D-10).
- E2 zero-one-many: Every status frame for one build reaches all of the owner's open sockets, once per socket.
- E3 empty: An owner with no open console sockets causes no error; `sendToOwner` returns 0 and the build continues.
- E3 loading: A tab subscribes on `wss.onopen` via `{init: owner}`; frames sent before subscription are not replayed.
- E3 error: An upgrade beyond the per-owner cap (≥ 4, recommended 10; each tab holds 2 sockets) is refused server-side with one log line and no UI effect (D-07).
- E3 populated: Two sockets on the same `/<owner>` path both connect and both receive the owner's frame; after one closes the other still receives; another owner's socket receives nothing (D-08).
- E3 zero-one-many: With one, two or more tabs open, each tab shows each frame exactly once.

## Decisions Recorded by This Contract

- **UI-D-01** No `services/console/src` change in Phase 43 beyond the committed `e43a94d` (D-01, D-14). Every visual
  property above is the existing rendering. Restyling, contrast and the quoted-JSON body form wait for the Phase 48
  Legacy batch.
- **UI-D-02** Escaping stays console-side through `thinxEscapeHtml`; toastr's `escapeHtml` option stays off (needed for
  the actionable buttons).
- **UI-D-03** Build toast copy is the existing frame bodies and reason codes (D-11). No friendlier failure copy in this
  phase.
- **UI-D-04** The frame rules F-1..F-5 are API-side and are part of NOTIF-03's acceptance: newly delivered toasts must
  not duplicate the terminal state or show a failed build as green.
- **UI-D-05** Multi-tab: one toast per frame per tab, no cross-tab sync, cap admits at least 2 tabs (4 sockets), and a
  refusal is silent in the UI with one server log line.
- **UI-D-06** Vue: no change and nothing to escape (D-02). The plan records it as a verified non-issue.
