## Warnings

### WR-01: Starting an impersonation leaves the admin's profile in the store, so the admin guard and the Sidebar decide for the impersonated session from the wrong account

**File:** `services/console/vue/src/pages/AdminUsers/AdminUsers.vue:110-129` (the identity switch), `services/console/vue/src/Routes.js:158-172` (the shortcut and the comment that names the reset points), `services/console/vue/src/components/Sidebar/Sidebar.vue:100-103`, `services/console/vue/src/components/ImpersonationBanner/ImpersonationBanner.vue:65-68`
**Issue:** `confirmImpersonate` obtains a token for a *different* user and calls `await this.persistSession({ accessToken, refreshToken: null })` then `this.$router.push('/app/dashboard')` (AdminUsers.vue:128-129). Nothing resets or refetches `profile/profile`: `persistSession` only stores tokens, the navigation stays under `/app` so `Layout` and `Header` are not remounted (`Header.mounted` is the only automatic refetch), and no component on the dashboard reads the profile. For the 15-minute impersonation window the store therefore holds the admin's own profile while every request is made as the impersonated non-admin:

- `Sidebar.isAdmin` (Sidebar.vue:100-103) keeps the ADMIN menu visible for a session the server treats as non-admin.
- `isAdminSession()` (Routes.js:161-173) takes its "non-empty profile, decided without a request" shortcut and lets `/app/admin/users` through; the page then fails with `Failed to load users.` because the API rejects the impersonated token.
- The Header shows the admin's name and avatar, not the impersonated user's (the banner shows the target, so the two disagree).
- `auth/setUser` is never updated for the impersonated identity either (pre-existing, same cause).

The reverse direction self-heals only partly: `ImpersonationBanner.exit` dispatches `clearSession` (not `logout`), pushes `/login`, and `Login.created` re-hydrates the admin's cookie session and pushes `/app/dashboard` *without* passing through `login()`, so the reset added by `9cb9ba2` does not run there. The Layout remount makes the Header refetch, so a Profile- or Transformers-page visit during the impersonation (both of which overwrite the store with the impersonated profile) is corrected within one request; until that request lands the shortcut bounces an admin deep link to the dashboard.

The fix commit's Routes.js comment (158-160) now records that the shortcut "relies on the store never holding a previous account" and lists `auth/logout` and the two sign-in pages as the places that guarantee it. Impersonation is the third identity switch in the console and guarantees nothing. As with iteration-1 WR-01 this is a UX-gate and identity-display defect, not an authorization bypass (the API enforces admin on every `/api/v2/admin` route), and the root pre-dates the phase; it is reported because the phase's fix declares the invariant complete and its tests (G7/G8) would stay green with this path broken.
**Fix:**
```js
// pages/AdminUsers/AdminUsers.vue confirmImpersonate(), after persistSession
await this.persistSession({ accessToken: access_token, refreshToken: null });
// The store must not keep the admin's profile for the impersonated session (48.1-REVIEW WR-01):
// reset, then read the impersonated user's profile with the new token; a failed read leaves {}
// and the guard/Sidebar fail closed until the Header retries.
this.$store.commit('profile/saveProfile', {});
try { await this.$store.dispatch('profile/fetchProfile'); } catch (_e) { /* fails closed */ }
this.$router.push('/app/dashboard');
```
```js
// components/ImpersonationBanner/ImpersonationBanner.vue exit()
async exit() {
  await this.clearSession();
  // The admin's own session is re-hydrated from the cookie on /login without login(): drop the
  // impersonated profile here so the guard fetches the admin's instead of deciding from it.
  this.$store.commit('profile/saveProfile', {});
  this.$router.push('/login');
},
```
Update the Routes.js comment to name impersonation start and exit as reset points, and add a G9 check to `audit-gaps-v118.cjs`: drive the real `confirmImpersonate` with a stub `impersonate` resolving a token and a `fetchProfile` that stores `{ admin: false }`, then assert the store no longer holds `admin: true` and the guard harness redirects `/app/admin/users` to `/app/dashboard` without a further request; drive `exit()` and assert one `profile/saveProfile {}` commit.

### IN-01: `refreshAfter` and the network-error literal are copy-pasted across five store modules

**File:** `services/console/vue/src/store/apikeys.js:13-21`, `services/console/vue/src/store/channels.js:5-13`, `services/console/vue/src/store/profile.js:5-13`, `services/console/vue/src/store/repositories.js:5-13` (plus the pre-existing copy in `store/enviros.js`)
**Issue:** Unchanged since iteration 1. Four byte-identical copies of `refreshAfter(dispatch, result)` differing only in the dispatched action name, and seven copies of `throw new Error('Could not reach the server.')` across `apikeys`, `channels`, `profile`, `repositories`, `enviros`, `devices`, `admin`. The harness's S3 already treats them as one contract; a future change (an error code, treating a non-2xx `status` as a refresh failure) must be made in five places.

The harness's `loadStore` strips `import` lines, so the shared module must be injected there the way `loadSfc` injects deps.

### IN-05: `create()` reloads the list a second time after `refreshAfter` already re-read it

**File:** `services/console/vue/src/pages/Apikeys/Apikeys.vue:78-83`, `services/console/vue/src/pages/Channels/Channels.vue:79-82`, `services/console/vue/src/pages/Repositories/Repositories.vue:120-123`
**Issue:** Unchanged since iteration 1. On a successful create the store's `createItem` runs `refreshAfter` (one `GET`) and the page then calls `this.loadData()` unconditionally (a second `GET`), discarding the `refreshed` flag. `deleteSelected` in the same files branches on `refreshed === false`; `create` expresses the same contract the old way. Behaviour is correct (a failed follow-up read still ends in the load-error state), but every create costs two list reads and the two handlers disagree.

### IN-06: `saveNotifications` ignores `refreshed: false` and never re-syncs the store copy

**Fix:** `if (result.refreshed === false) await this.loadProfile(); else this.profile = this.getProfile();` before setting the message, and add `saveNotifications` to the `saves` table in P5.
