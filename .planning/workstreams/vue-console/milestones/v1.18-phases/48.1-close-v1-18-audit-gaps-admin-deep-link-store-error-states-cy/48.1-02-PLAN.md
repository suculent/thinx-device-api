Close audit gap W2: the `apikeys`, `channels`, `repositories` and `profile` stores ignore a network failure and keep
stale or empty state, so the API Keys, Mesh Channels, Repositories and Profile pages show an empty or stale page with
no error. They now follow the contract the devices, enviros and admin stores got in 48-REVIEW CR-01: a request that

OAuthReturn and the store's own follow-up reads. An unhandled rejection from `fetchProfile` is exactly what ended
test 4 of the deep-link spec in 48-08, and a profile read must never block sign-in.

- PD-04 (contract): the four fetchers throw only on `result.networkError`, like `devices/fetchItems`,
  `enviros/fetchItems` and `admin/fetchUsers` (48-REVIEW CR-01). A refused reply keeps today's behaviour. Reason: the
  existing Cypress specs leave `GET /api/v2/source` to the catch-all (HTTP 500, not a network error) and DeviceDetail
  reads repositories through the same store, and the sign-in path must not change; the ROADMAP criterion names the
  network failing. `rsakeys` and `transformers` throw on every failure; copying that here would add a banner to
  DeviceDetail in every existing spec.
- PD-05 (state): a store leaves its state untouched when it throws (the pattern of rsakeys and transformers); the
  page clears its own copy of the rows. Follow-up reads after a write use the `refreshAfter` helper of
  `store/enviros.js` (file-local copy per store): a stored write resolves `refreshed: false` instead of rejecting.
- PD-06 (sign-in): a profile read that fails never blocks sign-in. Login and OAuthReturn continue to the dashboard;
  the Header retries on the next mount.
- PD-09 (adjacent defect, same lines): the three list pages copy `getItems()` into their own `items` only in
  `loadData`, so after a successful delete the store is refreshed but the page still shows the old array. The new
  `refreshed: false` branch needs the same re-sync, so the success branch re-syncs too (no extra request).
