## Warnings

### WR-01: The Header keeps showing the admin's name and avatar for the whole impersonated session; the fix's claim that Header and banner agree does not hold

**File:** `services/console/vue/src/components/Header/Header.vue:21`, `:26`, `:73`, `:88-93`, `:121-127`; `services/console/vue/src/components/Layout/Layout.vue:3-8`; `services/console/vue/src/pages/AdminUsers/AdminUsers.vue:129-141`; `services/console/vue/tests/unit/audit-gaps-v118.cjs:389-466` (G9)
**Issue:** The Header's identity display is not bound to the store. `data()` declares a local `profile: {}` (Header.vue:73); `mounted()` runs `fetchProfile()` once and copies the result with `this.profile = this.getProfile()` (Header.vue:121-127); the template renders `{{ this.profile.first_name }} {{ this.profile.last_name }}` (Header.vue:26) and the avatar through `avatarFallback`, a computed over the same local copy (Header.vue:88-93). `Layout.vue` mounts `<Header />` once above `<router-view />` with no `key` (Layout.vue:3-8), so navigating from `/app/admin/users` to `/app/dashboard` neither remounts it nor re-runs `mounted()`.

`confirmImpersonate` (AdminUsers.vue:129-141) therefore updates the Vuex store to the impersonated user's profile, and the Header continues to render the admin's name and avatar from its stale copy until the Layout is torn down at exit. For the 15-minute window the top bar says one identity while the banner directly beneath it says "Impersonating <target>", the opposite of what commit `47fffe7` ("a working read makes the impersonated user's profile authoritative for the session (Header name/avatar and banner agree)") and the fix report record. The reverse direction is fine: `exit()` leaves `/app`, so the Layout and Header remount and refetch.

G9 (audit-gaps-v118.cjs:389-466) asserts the store contents, the commit order and the guard's decision, and K1 asserts `mounted()` alone; nothing drives a store change against a mounted Header, so the suite stays green with this path broken. The root (a non-reactive copy of reactive state) pre-dates the phase and also means a name saved on the Profile page is not reflected in the Header until a remount, but the phase's fix claims this symptom resolved and it is the one iteration-2 symptom still observable.
**Fix:** Make the Header read the store reactively instead of copying it once:
```js
// components/Header/Header.vue
data() {
  return {};            // drop profile: {}
},
computed: {
  ...mapState("layout", { /* unchanged */ }),
  ...mapGetters("buildlog", { buildItems: "getItems" }),
  // Reactive: impersonation start (AdminUsers.confirmImpersonate), a Profile-page save and
  // the Header's own read all land here without a remount (48.1-REVIEW WR-01).
  profile() { return this.getProfile() || {}; },
  recentBuildCount() { /* unchanged */ },
  avatarFallback() { /* unchanged, reads this.profile */ },
},
mounted() {
  this.fetchProfile().catch(() => {
    // A failed read leaves the store (and so the name) as it is; the next mount retries.
  });
  this.$store.dispatch("buildlog/fetchBuildLog");
},
```
`mapGetters` in `methods` already exposes `getProfile()` as a function, so the computed can call it. Adjust K1 to assert the computed instead of a data field (or drive it through `Vue.extend(def)` and mutate the stubbed getter), and extend G9 with a mounted Header whose `getProfile` stub flips from `FIRST_ACCOUNT()` to the impersonated profile after `confirmImpersonate`, asserting the rendered name changes without a second `mounted()`. Then correct the fix report's claim or leave it to this review's record.
