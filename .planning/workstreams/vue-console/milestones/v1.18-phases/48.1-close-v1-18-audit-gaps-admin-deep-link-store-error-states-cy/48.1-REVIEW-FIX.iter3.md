### WR-01 (iteration 2): Starting an impersonation leaves the admin's profile in the store, so the admin guard and the Sidebar decide for the impersonated session from the wrong account

**Files modified (console submodule, paths relative to `services/console/`):**
`vue/src/pages/AdminUsers/AdminUsers.vue`, `vue/src/components/ImpersonationBanner/ImpersonationBanner.vue`,
`vue/src/Routes.js` (comment only), `vue/tests/unit/audit-gaps-v118.cjs`
**Commit:** `47fffe7` (`47fffe70ee496766a4e519c3f420be6784249716`, `git -C services/console log -1 --format=%G?` = `G`)
`fix(vue): reset the profile on both ends of admin impersonation (48.1-REVIEW WR-01)`
**Applied fix:** followed the review's recommended fix; the only adaptation is that `AdminUsers` reads the
profile through a `mapActions` binding (`fetchProfile: 'profile/fetchProfile'`), the convention Login and
Header use, rather than a raw `this.$store.dispatch`. The reset stays a `this.$store.commit`, as in Login.
- `AdminUsers.confirmImpersonate`: after `await this.persistSession({ accessToken, refreshToken: null })`
  (so the API client already carries the impersonated token) it commits `profile/saveProfile {}`, then
  `await this.fetchProfile()` inside a `try/catch` that absorbs a rejection, then pushes `/app/dashboard`.
  A refused or failed read therefore leaves `{}`: the Sidebar hides the ADMIN menu and the guard fetches and
  fails closed; a working read makes the impersonated user's profile authoritative for the session (Header
  name/avatar and banner agree). A failed profile read is not surfaced as an impersonation error.
- `ImpersonationBanner.exit()`: after `await this.clearSession()` it commits `profile/saveProfile {}` before
  pushing `/login`, because `Login.created` re-hydrates the admin's cookie session and goes to the dashboard
  without passing through `login()` (where the iteration-1 reset lives). The expiry-driven exit
  (`updateCountdown` -> `exit()`) takes the same path.
- `Routes.js`: the `isAdminSession` comment now names all four in-tab identity switches that keep the
  shortcut's invariant (`auth/logout`, `Login`/`OAuthReturn`, `AdminUsers.confirmImpersonate`,
  `ImpersonationBanner.exit`).
- `audit-gaps-v118.cjs`: new **G9** following the G7/G8 pattern (real component code via `loadSfc`, imports
  stubbed, `VueJwtDecode` stubbed for the banner). It drives the real `confirmImpersonate` twice (resolving
  and rejecting `fetchProfile`) with a stub `impersonate` resolving a token, and asserts the event order
  `persistSession -> saveProfile {} -> fetchProfile -> push /app/dashboard`, exactly one reset commit, that
  the read observed `{}`, that the store ends as the impersonated profile (or `{}` on rejection), no other
  `$store` commit and no error message. The guard harness seeded with each result redirects
  `/app/admin/users` to `/app/dashboard` without a request (impersonated profile) or fetches and fails closed
  (`{}`). It then drives the real `exit()` and asserts `clearSession -> saveProfile {} -> push /login` with
  one reset commit. The file header and the WR-01 comment block were updated to mention G9.
- Not changed (scope): `auth/setUser` is still not updated for the impersonated identity. The review lists
  it as pre-existing with the same cause but did not include it in the recommended fix; nothing in the
  console reads `auth.user` for a decision.
