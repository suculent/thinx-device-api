## Warnings

### WR-01: A previous account's profile survives sign-out and decides the admin guard and Sidebar for the next account

**File:** `services/console/vue/src/Routes.js:159-171`, `services/console/vue/src/pages/Login/Login.vue:214-220`, `services/console/vue/src/pages/OAuthReturn/OAuthReturn.vue:190-196`, `services/console/vue/src/store/auth.js:95-104` (root cause, not changed by this phase)
**Issue:** `auth/clearSession` (the only teardown path; `auth/logout` delegates to it) resets `user`, `accessToken` and `refreshToken` but never resets `profile/profile`. After an in-tab sign-out (`Header.logout` pushes `/login` without a reload) the store still holds the signed-out account's profile. The phase then makes that stale object authoritative in two new ways:
- `isAdminSession()` (Routes.js:162) only fetches while the store holds the initial empty object; a non-empty stale profile is "decided without a request", so a second account that signs in gets the first account's `admin === true` verdict until something overwrites it.
- Login.vue:215-219 and OAuthReturn.vue:191-195 now swallow a failed `fetchProfile` and continue to `setUser(this.getProfile())` and the dashboard. When the read fails (offline blip, aborted by the navigation), nothing overwrites the stale profile. `Header.mounted` retries once per Layout mount, so under `/app/*` there is no further retry until a reload or a Profile-page visit.

Observable effect for the second account on that path: the Sidebar's `isAdmin` computed (`Sidebar.vue:100-103`) shows the admin menu, `/app/admin/users` renders its shell (the API then rejects the list), and `auth/setUser` is committed with the other account's identity. The root cause pre-dates the phase (before it, `fetchProfile` resolved silently on a network failure with the same stale result), but this phase's guard shortcut and the explicit "sign-in continues" decision turn the stale store into the deciding input, and the phase's own test G4 (`audit-gaps-v118.cjs:193-205`) pins the shortcut without covering sign-out.

Do not reset the profile inside `clearSession` itself: `scheduleExpiry.expire` (auth.js:128-131) calls `clearSession` and then silently re-hydrates the same account; wiping the profile there would blank the Sidebar admin menu for the rest of the session, since the Header does not refetch.
**Fix:**
```js
// store/auth.js — explicit sign-out only
async logout({ dispatch, commit }) {
  try { await fetch(this.$api.composePath('/logout'), { method: 'GET', credentials: 'include', redirect: 'manual' }); }
  catch (_error) { /* unreachable server: still drop the local session */ }
  await dispatch('clearSession');
  // The next account must not inherit this one's profile (admin flag, name, avatar).
  commit('profile/saveProfile', {}, { root: true });
},
```
```js
// pages/Login/Login.vue login() and pages/OAuthReturn/OAuthReturn.vue complete(), before the read
this.$store.commit('profile/saveProfile', {});   // a failed read below leaves {} , never a stale account
try { await this.fetchProfile(); } catch (profileError) { /* sign-in continues; Header retries */ }
```
Add a G-check to `audit-gaps-v118.cjs`: seed `profile: { admin: true }`, run `auth/logout` (or the Login path with a rejecting `fetchProfile`), then assert the guard dispatches `profile/fetchProfile` and redirects to `/app/dashboard`.

### IN-01: `refreshAfter` and the network-error literal are copy-pasted across five store modules

**File:** `services/console/vue/src/store/apikeys.js:13-21`, `services/console/vue/src/store/channels.js:5-13`, `services/console/vue/src/store/profile.js:5-13`, `services/console/vue/src/store/repositories.js:5-13` (plus the pre-existing copy in `store/enviros.js:5-13`)
**Issue:** Four new byte-identical copies of the `refreshAfter(dispatch, result)` helper (differing only in the action name string) and seven copies of `throw new Error('Could not reach the server.')` across `apikeys`, `channels`, `profile`, `repositories`, `enviros`, `devices`, `admin`. The unit harness S3 already treats them as one contract; a future change (e.g. attaching an error code, or treating a non-2xx `status` as a refresh failure) has to be made in five places and the fifth is easy to miss.
**Fix:** Extract once, e.g. `src/store/network.js`:
```js
export const NETWORK_ERROR_MESSAGE = 'Could not reach the server.';
export function throwIfUnreachable(result) { if (result && result.networkError) throw new Error(NETWORK_ERROR_MESSAGE); }
export async function refreshAfter(dispatch, result, action) {
  if (!result || !result.success) return result;
  try { await dispatch(action); } catch (e) { return Object.assign({}, result, { refreshed: false }); }
  return result;
}
```
and call `refreshAfter(dispatch, result, 'fetchItems')` / `'fetchProfile'` / `'fetchRepositories'`. The harness's `loadStore` strips `import` lines, so the shared module must be injected there the way `loadSfc` injects deps.

### IN-03: `deep-link.spec.js` exercises the re-stubbing trap its own support file warns about

**File:** `services/console/vue/cypress/integration/deep-link.spec.js:7-10` and `:61-63`
**Issue:** The outer `beforeEach` calls `cy.stubThinxApi()` and the admin `describe`'s `beforeEach` calls `cy.stubThinxApi({ profile: 'api/profile-admin.json' })` on top of it. `api-stubs.js:83-89` documents this exact double call as the way bespoke intercepts get silently swallowed by the fresh catch-all. Today nothing is registered between the two calls so the tests pass (and the duplicated aliases resolve to the newest route), but any bespoke `cy.intercept` later added to the outer `beforeEach` would stop matching inside the admin block with no error.
**Fix:** Drop `cy.stubThinxApi()` from the outer `beforeEach` (keep the viewport) and call it once per `describe` with the fixture that block needs; the two non-admin blocks call `cy.stubThinxApi()`, the admin block calls `cy.stubThinxApi({ profile: 'api/profile-admin.json' })`.

### IN-05: `create()` reloads the list a second time after `refreshAfter` already re-read it

**File:** `services/console/vue/src/pages/Apikeys/Apikeys.vue:77-83`, `services/console/vue/src/pages/Channels/Channels.vue:78-82`, `services/console/vue/src/pages/Repositories/Repositories.vue:119-123`
**Issue:** On a successful create the store's `createItem` now runs `refreshAfter` (one `GET`), and the page then calls `this.loadData()` unconditionally (a second `GET`), discarding the `refreshed` flag the phase introduced. `deleteSelected` in the same files was rewritten to branch on `refreshed === false` and otherwise read `this.getItems()`; `create` was left on the old always-reload path. Behaviour is correct (a failed follow-up read still ends in the load-error state because `loadData` fails too), but the two handlers now express the same contract two different ways, and every create costs two list reads.
**Fix:** Mirror `deleteSelected`:
```js
if (result.success) {
  /* ...modal handling... */
  if (result.refreshed === false) await this.loadData();
  else this.items = this.getItems();
}
```
and extend P4 in the harness to cover `create`.

### IN-06: `saveNotifications` ignores `refreshed: false` and never re-syncs the store copy

**File:** `services/console/vue/src/pages/Profile/Profile.vue:343-357`
**Issue:** `saveNotifications` calls `updateProfile`, which this phase changed to resolve `{ success: true, refreshed: false }` when the follow-up `fetchProfile` fails. The two sibling handlers in the same commit (`saveProfile`:327, `saveAvatar`:376) branch on that flag and reload; `saveNotifications` shows `Notification preferences saved.` and leaves the store's `profile.info.notifications` at its pre-save value, with no load error. Not user-visible today: the page renders the flags from `notifForm`, no other component reads `info.notifications`, and the next route visit refetches. It is the one `updateProfile` caller the phase left on the old contract, and the P5 harness check does not cover it.
**Fix:** Mirror the sibling handlers: `if (result.refreshed === false) await this.loadProfile(); else this.profile = this.getProfile();` before setting the message, and add `saveNotifications` to the `saves` table in P5 (`audit-gaps-v118.cjs:926-929`).
